# WebSocket сообщений

Переписки нет в `swagger.json`: HTTP отдает только токен, а сам обмен
сообщениями идет по WebSocket, контракт которого учебное API нигде не
публикует.

**Статус: разведка, не спецификация.** Все, что ниже, снято 2026-09-04 с
чужой рабочей реализации поверх того же API -
[krasotun/middle.messenger](https://github.com/krasotun/middle.messenger)
(`src/api/messages-api.ts`, `src/controllers/messages-controller.ts`,
`src/model/Message.ts`). Это наблюдение за работающим клиентом, а не
обязательство сервера. Каждый пункт подтверждается руками при реализации; что
не подтвердилось - правится здесь же.

## Подключение

Токен - `POST /chats/token/{id}` (`ChatsMessagesTokenResponse.token`), живет
до переподключения и запрашивается заново на каждый **Чат**.

```
wss://ya-praktikum.tech/ws/chats/{userId}/{chatId}/{token}
```

URL собирается из `basePath` заменой схемы `http` -> `ws` и отбрасыванием
хвоста `/api/v2`. `userId` - id **Текущего пользователя**.

Сокет один на приложение: смена **Выбранного чата** закрывает предыдущее
соединение и открывает новое.

## Кадры от клиента

| Кадр                                        | Когда              |
| ------------------------------------------- | ------------------ |
| `{ "type": "get old", "content": "0" }`     | сразу после `open` |
| `{ "type": "message", "content": "текст" }` | отправка сообщения |
| `{ "type": "ping" }`                        | каждые 10 секунд   |

`content` у `get old` - это offset, и он строка, а не число. Отправка
проверяет `readyState === OPEN`; в закрытый сокет писать нельзя.

Ping обязателен: без него сервер рвет соединение. Интервал 10 секунд взят из
той же реализации, верхняя граница неизвестна.

## Кадры от сервера

Приходит JSON, и его форма зависит от кадра:

- **массив** - история в ответ на `get old`, отсортированная от новых к
  старым, то есть для показа ее нужно развернуть;
- **объект с `type: "message"`** - одно новое сообщение;
- **все остальное** (`pong`, `user connected`) - служебные кадры, которые
  клиент игнорирует.

Сообщение по составу совпадает с `ChatMessage` из `swagger.json` минус поле
`file`: `id`, `user_id`, `chat_id`, `time`, `type`, `content`. Тип `file`
объявлен в swagger, но через сокет в такой реализации не отправляется.

## Что WebSocket не делает

Сокет не обновляет `last_message` и `unread_count` в списке **Чатов**: эти
поля отдает только `GET /chats`. Разведанная реализация решает это в лоб -
держит маркер `messagesUpdatedAt` и перезапрашивает весь список на каждое
входящее сообщение.

Нам это не образец, а предупреждение: связь между сокетом и списком **Чатов**

- отдельное решение, и принимать его нужно в `design.md` соответствующего
  change, а не копировать.
