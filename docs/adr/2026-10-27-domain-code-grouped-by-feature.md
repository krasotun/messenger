# Код домена раскладывается по фичам, слои держатся суффиксами файлов

- Дата: 2026-10-27
- Статус: superseded by [2026-10-28-page-part-stores-and-folder-boundaries](./2026-10-28-page-part-stores-and-folder-boundaries.md)
- Issue: #267

## Контекст

Внутри домена код лежал по слоям (`presentation/`, `application/`,
`infrastructure/`), а в слоях - по сценариям. Один сценарий жил в двух-трех
местах под одним именем (`chat-list` в `application` и в `presentation`, семь
одинаковых имен в `application` и `infrastructure` у `identity-access`), и по
дереву стало трудно понять, какой сервис за что отвечает.

## Решение

Домены остаются, внутри домена - папка на фичу, где компонент и его сервисы
лежат рядом; модели и порты шлюзов - в корне домена, HTTP - в `api/`. Папка
называется по сервису: у сервиса без своих компонентов тоже есть папка
(`delete-chat/`), а не место у компонента, который его вызывает, - иначе
искать его приходится по тому, кто его зовет. Правила
слоев ESLint проверяет по суффиксам файлов (`*.service.ts`, `*.state.ts`,
`*.gateway.ts`, `*.type.ts`), а не по папкам.

## Причины

Официальный style guide Angular советует группировать по фичам и не заводить
папки по типу кода
(<https://angular.dev/style-guide#organize-your-project-by-feature-areas>).
Слои-папки - те же папки по типу, только с другими названиями. Фича-первая
раскладка убирает повтор имен: имя сценария встречается один раз, а внутри
папки файлы различаются суффиксом.

Тот же гайд просит не копить в одной папке столько файлов, что по ней трудно
ориентироваться. Поэтому `api/` делится на подпапки по ресурсам контракта
(`api/auth/`, `api/user/`), когда в нем становится тесно; `identity-access`
делится сразу (около 30 файлов), `chats` пока плоский. Делим по мере роста, а
не заранее.

Сами границы слоев - не повод для папок: то, что application не знает про
формы и DOM и ходит наружу только через шлюз (`2026-05-10-domain-talks-to-the-world-through-gateways.md`),
проверяется по суффиксу файла так же надежно. Слова «application» и
«infrastructure» в том ADR и в `CONTEXT.md` теперь означают роль файла, а не
папку.

Отклонили:

- **Оставить слои, разложить только `infrastructure` по ресурсам** (решение
  24-10) - убирает повтор между `application` и `infrastructure`, но не между
  `application` и `presentation`.
- **Сервис на ресурс вместо сервиса на сценарий** - у каждой операции здесь
  свое состояние (статус, ошибка), и один класс собрал бы их все. Число
  сервисов этим ADR не меняется.
- **Feature-Sliced Design** - режет домен по слоям `entities`, `features`,
  `widgets`, единица в нем - тот же сценарий, а запрет импортов между
  слайсами одного слоя ломает связь `chats` -> `identity-access`.

Чем пожертвовали: ESLint отличает компонент от сервиса только по отсутствию
суффикса в пути импорта, поэтому файл application без суффикса правило
пропустит. Суффикс у сервисов, состояний, шлюзов и моделей поэтому
обязателен. Это расходится с CLI начиная с v20, который суффиксы не
добавляет; для сервисов разрыв закрывает настройка схематика в `angular.json`
(`type: "service"`), и `ng g service` создает `*.service.ts` сам. До этого ADR
суффиксы уже стояли у всех файлов application без исключений - решение
закрепляет сложившуюся практику.
