# Сессия живет в cookie бэкенда, фронтенд не хранит токены

- Дата: 2026-05-12
- Статус: accepted
- Issue: -

ADR заведен задним числом 2026-08-27 (#69): решение принято до внедрения
OpenSpec, дата взята по первому появлению `withCredentials` в коде (`8f73c50`).

## Контекст

Учебный API Яндекс.Практикума аутентифицирует запросы session cookie: `signin`
устанавливает ее, `GET /auth/user` по ней отвечает текущим пользователем либо
`401`. Фронтенду нужно было решить, где живет знание о том, что посетитель -
**Текущий пользователь**.

## Решение

Единственный владелец сессии - бэкенд, состояние хранится в cookie. Приложение
сессию не создает и не хранит, а только выясняет ее наличие через
**Восстановление сессии** и отражает во **Статусе сессии**.

## Причины

Cookie ставит и снимает сам бэкенд, а `HttpOnly`-cookie недоступна скриптам -
XSS не вычитает из нее сессию. Любое собственное хранилище на фронтенде было бы
второй копией правды, которая расходится с бэкендом при истечении или отзыве
сессии на его стороне.

Чем пожертвовали: приложение не может показать сессию, не сходив в сеть, -
отсюда состояние `Unknown` и запрос на старте, без которого не отрисовать
маршруты. И запросы обязаны идти с credentials, то есть API обязан отдавать
`Access-Control-Allow-Credentials` и конкретный origin вместо `*`.

Альтернативы:

- _Токен в `localStorage` или `sessionStorage`_ - типовой путь учебных
  проектов, отклонен: доступен любому скрипту на странице, живет дольше
  серверной сессии и требует ручной инвалидации.
- _Хранить признак «вошел» в приложении, чтобы не ходить в сеть на старте_ -
  отклонен: признак врет ровно в тот момент, когда бэкенд сессию уже закрыл,
  и guard пускает на закрытые маршруты.

## Следствия

- `apiRequestInterceptor` ставит `withCredentials: true` всем запросам к API:
  раз сессию носит cookie, транспорт обязан ее передавать.
- Статус сессии различает `Unknown` и `Anonymous`: незнание и установленный
  факт отсутствия - разные вещи, когда правда живет на другой стороне.
