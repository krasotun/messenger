# identity-access

## Purpose

Регистрация, вход, восстановление и завершение пользовательской сессии, а также
политика доступа к маршрутам приложения. Сессия принадлежит бэкенду и хранится в
cookie; фронтенд не хранит токены самостоятельно.

## Requirements

### Requirement: Регистрация нового пользователя

Приложение SHALL позволять зарегистрировать нового пользователя по данным:
`firstName`, `secondName`, `login`, `email`, `password`, `phone`. Все поля
обязательны. `email` MUST соответствовать `^\S+@\S+$`, `phone` MUST
соответствовать телефонному формату длиной от 10 до 15 символов. Уникальность
логина проверяет бэкенд.

#### Scenario: Успешная регистрация

- **WHEN** пользователь отправляет валидную форму регистрации и бэкенд отвечает `200 OK`
- **THEN** flow переходит в состояние `Success` и приложение переводит пользователя на `/sign-in`

#### Scenario: Отправка формы с невалидными данными

- **WHEN** пользователь отправляет форму регистрации с ошибками валидации
- **THEN** запрос к бэкенду не отправляется, все поля помечаются как touched и под ними показываются сообщения об ошибках

#### Scenario: Бэкенд отклоняет регистрацию

- **WHEN** бэкенд отвечает ошибкой с полем `reason`
- **THEN** flow переходит в `Error` и пользователю показывается сообщение из `reason`

#### Scenario: Ошибка без сообщения от бэкенда

- **WHEN** бэкенд отвечает ошибкой без `reason`
- **THEN** пользователю показывается generic-сообщение об ошибке регистрации

#### Scenario: Форма заблокирована во время отправки

- **WHEN** запрос регистрации выполняется
- **THEN** форма недоступна для редактирования до получения ответа

### Requirement: Вход существующего пользователя

Приложение SHALL авторизовывать пользователя по `login` и `password`. Оба поля
обязательны. Успех входа определяется не телом ответа, а успешным восстановлением
текущей сессии после `200 OK`.

#### Scenario: Успешный вход

- **WHEN** бэкенд принимает данные входа и последующее восстановление сессии возвращает статус `Authenticated`
- **THEN** flow переходит в `Success`, состояние flow сбрасывается и приложение переводит пользователя на `/`

#### Scenario: Вход принят, но сессия не восстановлена

- **WHEN** бэкенд ответил `200 OK`, но восстановление сессии не дало статус `Authenticated`
- **THEN** flow переходит в `Error` и показывается сообщение о неудачном входе

#### Scenario: Неверные учетные данные

- **WHEN** бэкенд отклоняет вход
- **THEN** flow переходит в `Error` и показывается сообщение из `reason`, а при его отсутствии - generic-сообщение

#### Scenario: Отправка пустой формы входа

- **WHEN** пользователь отправляет форму входа с незаполненными полями
- **THEN** запрос не отправляется и под полями показываются сообщения об обязательности

### Requirement: Восстановление текущей сессии

Приложение SHALL восстанавливать текущую сессию через `GET /auth/user` с
передачей cookie до отрисовки маршрутов. Статус сессии принимает значения
`Unknown`, `Loading`, `Authenticated`, `Anonymous`. Токены сессии MUST NOT
сохраняться в `localStorage` или `sessionStorage`.

Отказ бэкенда при восстановлении сессии на старте приложения MUST NOT
прерывать запуск: приложение SHALL стартовать со статусом `Anonymous`.
Восстановление сессии, вызванное не стартом приложения, SHALL пробрасывать
ошибку вызывающей стороне.

#### Scenario: Активная сессия существует

- **WHEN** бэкенд возвращает текущего пользователя
- **THEN** статус сессии становится `Authenticated`, а текущий пользователь сохраняется в состоянии приложения

#### Scenario: Активной сессии нет

- **WHEN** бэкенд отвечает `401 Unauthorized`
- **THEN** статус сессии становится `Anonymous`, а текущий пользователь очищается

#### Scenario: Ошибка при восстановлении сессии

- **WHEN** запрос восстановления сессии завершается технической ошибкой
- **THEN** текущий пользователь очищается, статус становится `Anonymous`, а ошибка пробрасывается вызывающей стороне

#### Scenario: Бэкенд недоступен при старте приложения

- **WHEN** посетитель открывает приложение и запрос восстановления сессии завершается технической ошибкой
- **THEN** приложение запускается, статус сессии становится `Anonymous` и посетитель видит экран входа, а не пустую страницу

#### Scenario: Вход после неудачного восстановления сессии

- **WHEN** посетитель отправляет форму входа, а бэкенд по-прежнему недоступен
- **THEN** флоу отправки переходит в `Error` и показывается сообщение об ошибке, то есть проброс ошибки для входа сохраняется

### Requirement: Завершение сессии

Приложение SHALL позволять авторизованному пользователю выйти из аккаунта через
меню текущего пользователя.

#### Scenario: Успешный выход

- **WHEN** пользователь подтверждает выход и бэкенд завершает сессию
- **THEN** текущий пользователь очищается, статус становится `Anonymous` и пользователь переводится на `/sign-in`

#### Scenario: Выход завершился ошибкой

- **WHEN** запрос выхода завершается ошибкой
- **THEN** локальная сессия все равно очищается и пользователь переводится на `/sign-in`

### Requirement: Отображение текущего пользователя

Приложение SHALL показывать авторизованному пользователю его аватар в шапке.
Подпись формируется из первого непустого значения: `displayName`, `firstName`,
`login`, `email`. Бэкенд отдает `avatar` относительным путем; приложение SHALL
показывать его как изображение по абсолютному URL, полученному из этого пути.

#### Scenario: У пользователя есть аватар

- **WHEN** текущий пользователь загружен и у него задан `avatar`
- **THEN** в шапке показывается изображение аватара по абсолютному URL с подписью имени пользователя

#### Scenario: У пользователя нет аватара

- **WHEN** текущий пользователь загружен без `avatar`
- **THEN** показывается заглушка с первой буквой имени в верхнем регистре

### Requirement: Редактирование профиля текущего пользователя

Авторизованный пользователь SHALL иметь возможность изменить свои данные:
`firstName`, `secondName`, `displayName`, `login`, `email`, `phone`. Поля `id` и
`avatar` MUST NOT редактироваться в этом сценарии. Форма редактирования SHALL
предзаполняться данными текущего пользователя.

#### Scenario: Открытие формы редактирования

- **WHEN** авторизованный пользователь открывает редактирование профиля
- **THEN** форма показывается с текущими значениями редактируемых полей

#### Scenario: Меню закрывается при открытии формы

- **WHEN** пользователь выбирает редактирование профиля в меню текущего пользователя
- **THEN** меню закрывается, а форма редактирования открывается

#### Scenario: Успешное сохранение

- **WHEN** пользователь сохраняет валидные изменения и бэкенд подтверждает обновление
- **THEN** текущая сессия обновляется данными из ответа бэкенда, а вызывающая сторона получает обновленного текущего пользователя

#### Scenario: После успешного сохранения не происходит навигации

- **WHEN** обновление профиля завершилось успешно
- **THEN** переход на другой маршрут не выполняется, а форма редактирования может быть закрыта

#### Scenario: Обновленные данные видны в интерфейсе

- **WHEN** профиль успешно обновлен
- **THEN** отображение текущего пользователя показывает новые значения без перезагрузки страницы

#### Scenario: Бэкенд отклоняет сохранение

- **WHEN** бэкенд отвечает ошибкой
- **THEN** текущая сессия не меняется, показывается сообщение из `reason` (а при его отсутствии - generic-сообщение), и введенные значения остаются в форме для исправления

#### Scenario: Отправка невалидной формы

- **WHEN** пользователь сохраняет форму с ошибками валидации
- **THEN** запрос к бэкенду не отправляется и показываются сообщения об ошибках полей

#### Scenario: Отмена редактирования

- **WHEN** пользователь закрывает форму, не сохранив изменения
- **THEN** текущая сессия остается прежней

### Requirement: Смена пароля текущим пользователем

Текущий пользователь SHALL иметь возможность сменить свой пароль, подтвердив
старый пароль и задав новый. Форма SHALL требовать три значения: старый
пароль, новый пароль и повтор нового пароля. Повтор MUST NOT отправляться на
бэкенд: он проверяется только на клиенте. Все три поля обязательны, других
правил к новому паролю не предъявляется - решение о его пригодности принимает
бэкенд. Смена пароля MUST NOT изменять профиль и MUST NOT завершать текущую
сессию.

#### Scenario: Открытие формы смены пароля

- **WHEN** текущий пользователь выбирает смену пароля в меню текущего пользователя
- **THEN** меню закрывается, а форма смены пароля открывается с пустыми полями

#### Scenario: Успешная смена пароля

- **WHEN** текущий пользователь отправляет валидную форму и бэкенд подтверждает смену
- **THEN** форма закрывается, текущая сессия остается активной, а отображение текущего пользователя не меняется

#### Scenario: После успешной смены не происходит навигации

- **WHEN** смена пароля завершилась успешно
- **THEN** переход на другой маршрут не выполняется

#### Scenario: Бэкенд отклоняет смену пароля

- **WHEN** бэкенд отвечает ошибкой, в том числе на неверный старый пароль
- **THEN** форма остается открытой с введенными значениями и показывает сообщение из `reason`, а при его отсутствии - generic-сообщение

#### Scenario: Повтор не совпадает с новым паролем

- **WHEN** текущий пользователь отправляет форму, в которой повтор нового пароля отличается от нового пароля
- **THEN** запрос к бэкенду не отправляется и показывается ошибка поля повтора

#### Scenario: Отправка формы с незаполненными полями

- **WHEN** текущий пользователь отправляет форму, где хотя бы одно поле пустое
- **THEN** запрос к бэкенду не отправляется и показываются сообщения об ошибках полей

#### Scenario: Форма заблокирована во время отправки

- **WHEN** запрос на смену пароля выполняется
- **THEN** поля и кнопка отправки недоступны до получения ответа

#### Scenario: Отмена смены пароля

- **WHEN** текущий пользователь закрывает форму, не отправив ее
- **THEN** пароль и текущая сессия остаются прежними

#### Scenario: Повторное открытие формы после ошибки

- **WHEN** текущий пользователь закрывает форму после ошибки и открывает ее снова
- **THEN** форма показывается с пустыми полями и без сообщения об ошибке

### Requirement: Смена аватара текущим пользователем

Текущий пользователь SHALL иметь возможность сменить свой аватар, выбрав файл
изображения. Допустимые форматы: JPEG, JPG, PNG, GIF, WebP. Смена аватара -
действие, независимое от **Редактирования профиля**: MUST NOT изменять
остальные поля профиля, MUST NOT завершать текущую сессию и MUST NOT требовать
отправки формы редактирования профиля. Форма смены аватара SHALL находиться в
той же модалке, что и форма редактирования профиля, не будучи ее частью.

#### Scenario: Открытие формы смены аватара

- **WHEN** текущий пользователь открывает редактирование профиля
- **THEN** вместе с формой редактирования показывается форма смены аватара без выбранного файла

#### Scenario: Выбор файла показывает превью

- **WHEN** текущий пользователь выбирает файл поддерживаемого формата
- **THEN** форма показывает превью выбранного изображения вместо текущего аватара

#### Scenario: Выбор файла неподдерживаемого формата

- **WHEN** текущий пользователь выбирает файл формата, не входящего в список допустимых
- **THEN** файл не отправляется на бэкенд и показывается сообщение о недопустимом формате

#### Scenario: Успешная смена аватара

- **WHEN** текущий пользователь отправляет форму с выбранным файлом и бэкенд подтверждает смену
- **THEN** форма смены аватара сбрасывается к состоянию без выбранного файла, модалка не закрывается, текущая сессия обновляется данными из ответа бэкенда, а отображение текущего пользователя показывает новый аватар без перезагрузки страницы

#### Scenario: После успешной смены не происходит навигации

- **WHEN** смена аватара завершилась успешно
- **THEN** переход на другой маршрут не выполняется

#### Scenario: Бэкенд отклоняет смену аватара

- **WHEN** бэкенд отвечает ошибкой
- **THEN** форма остается открытой с выбранным файлом и показывает сообщение из `reason`, а при его отсутствии - generic-сообщение

#### Scenario: Отправка формы без выбранного файла

- **WHEN** текущий пользователь отправляет форму, не выбрав файл
- **THEN** запрос к бэкенду не отправляется и показывается сообщение о необходимости выбрать файл

#### Scenario: Форма заблокирована во время отправки

- **WHEN** запрос на смену аватара выполняется
- **THEN** поле выбора файла и кнопка отправки недоступны до получения ответа

#### Scenario: Отмена смены аватара

- **WHEN** текущий пользователь выбрал файл, но закрыл модалку профиля, не отправив форму смены аватара
- **THEN** аватар и текущая сессия остаются прежними

#### Scenario: Повторное открытие формы после ошибки

- **WHEN** текущий пользователь закрывает модалку профиля после ошибки смены аватара и открывает редактирование профиля снова
- **THEN** форма смены аватара показывается без выбранного файла и без сообщения об ошибке

### Requirement: Политика доступа к маршрутам

Приложение SHALL ограничивать доступ к маршрутам по статусу текущей сессии.

#### Scenario: Гость открывает защищенный маршрут

- **WHEN** пользователь без статуса `Authenticated` открывает `/`
- **THEN** происходит редирект на `/sign-in`

#### Scenario: Авторизованный пользователь открывает страницы входа

- **WHEN** пользователь со статусом `Authenticated` открывает `/sign-in` или `/sign-up`
- **THEN** происходит редирект на `/`

#### Scenario: Авторизованный пользователь открывает защищенный маршрут

- **WHEN** пользователь со статусом `Authenticated` открывает `/`
- **THEN** маршрут открывается внутри authenticated shell

### Requirement: Сообщения об ошибках от бэкенда

Инфраструктурный слой SHALL приводить ошибки HTTP к `ApplicationError` с
человекочитаемым сообщением. Тело ошибки SHALL разбираться и тогда, когда
ответ читается как текст: у запросов с `responseType: 'text'` тело приходит
строкой и не разбирается HttpClient, поэтому `reason` из такого ответа
пользователь MUST видеть так же, как из разобранного JSON.

#### Scenario: Ответ содержит reason

- **WHEN** бэкенд возвращает тело ошибки с полем `reason`
- **THEN** `ApplicationError` содержит текст из `reason` и исходную ошибку как причину

#### Scenario: Тело ошибки пришло текстом

- **WHEN** бэкенд возвращает ошибку на запрос, читаемый как текст, и в теле есть `reason`
- **THEN** `ApplicationError` содержит текст из `reason`, а не generic-сообщение

#### Scenario: Ответ не содержит reason

- **WHEN** тело ошибки отсутствует, не является JSON или в нем нет `reason`
- **THEN** `ApplicationError` содержит fallback-сообщение, заданное вызывающим use case

### Requirement: Поиск пользователей по логину

Приложение SHALL находить **Пользователей** по началу их **Логина** и SHALL
отдавать их только на чтение: **Профиль** чужого **Пользователя** не
редактируется.

Отсутствие совпадений SHALL быть пустым результатом, а не **Ошибкой
приложения**.

#### Scenario: Совпадения найдены

- **WHEN** запрошен поиск по началу **Логина**
- **THEN** возвращаются найденные **Пользователи**

#### Scenario: Совпадений нет

- **WHEN** ни один **Логин** не начинается с запрошенного
- **THEN** возвращается пустой результат
- **AND** **Ошибка приложения** не возникает

#### Scenario: Поиск не удался

- **WHEN** внешнее API отвечает ошибкой
- **THEN** возвращается **Ошибка приложения**
