## Context

Мотивация - в `proposal.md`, требования - в дельтах спек этого change.

Что ограничивает подход:

- `ModalService.open()` сейчас возвращает `void`, а `ModalRef` умеет только
  `close()`; узнать исход открытого окна вызывающему нечем.
- Исход действия в проекте сообщается **Уведомлением** через порт `NOTIFIER`
  (см. `docs/adr/2026-09-06-use-cases-report-outcome-through-a-notifier-port.md`),
  а успех формы - однократным событием `succeeded$`. Домен чатов уже так
  устроен в `CreateChatService` и `AddChatUserService`.
- `application` не знает про DOM, Overlay и `ModalRef` - это закреплено в
  ESLint. Значит подтверждение спрашивает `presentation`, а не use case.
- Внешнее API: `DELETE /chats` с телом `{ chatId }`, «Delete works only for
  admin role». Список **Чатов** приходит из `GET /chats`.
- Макет: канвас экрана чатов, артборды `HeaderDeleteVisibility` и `DeleteChat`
  - https://claude.ai/code/artifact/fcd629d1-a834-4059-981c-16f2a914ca55 -
    обновлен под это решение, тексты окна и вид кнопки берутся оттуда.

## Goals / Non-Goals

**Goals:**

- Подтверждение переиспользуемо: следующий потребитель получает его одной
  строкой, не зная про `ModalService`.
- Право на **Удаление чата** известно из уже загруженного списка **Чатов**, без
  дополнительного запроса.
- Исход **Удаления чата** виден независимо от того, что осталось на экране.

**Non-Goals:**

- Архивация **Чата** (`/chats/archive`) и выход из **Чата** - отдельные
  действия внешнего API, в этот change не входят.
- Передача положения **Создателя чата** другому **Участнику чата** - внешнее
  API такого действия не имеет.
- Обобщение `ModalService` до произвольного типизованного результата на все
  случаи: вводим ровно то, что нужно подтверждению.

## Decisions

### Право на удаление берем из `created_by` в `GET /chats`

**Создатель чата** определяется сравнением `created_by` **Чата** с `id`
**Текущего пользователя** из `CurrentSessionService`. Модель `Chat` получает
поле автора, маппер - его чтение из `ChatDto`.

Альтернатива - `role: 'admin'` из `GET /chats/{id}/users`. Поле объявлено в
контракте обязательным и прямо соответствует формулировке «works only for admin
role», но эндпоинт пагинируется (`offset`, `limit`), а мы зовем его без них:
в **Чате**, не помещающемся в страницу ответа, себя в списке можно не найти, и
«не нашли» стало бы неотличимо от «не вправе». `created_by` приходит вместе со
списком и от размера **Чата** не зависит.

Цена: в `docs/api/swagger.json` поле `created_by` есть в `example`
`ChatsResponse`, но отсутствует в его `properties`. Если API его не вернет,
действие не покажется никому - проверяется первым же запросом на реальном API.

Порог `docs/adr/README.md` решение не проходит: смена источника права - это
одно поле в модели и маппере, откатить дешево. ADR не заводим.

### Подтверждение - сервис `shared/ui`, а не компонент на откуп домену

Вводится:

| Имя                   | Ответственность                            | Слой        |
| --------------------- | ------------------------------------------ | ----------- |
| `ConfirmationService` | спросить подтверждение и вернуть ответ     | `shared/ui` |
| `ConfirmationDialog`  | содержимое окна подтверждения              | `shared/ui` |
| `CONFIRMATION_DATA`   | тексты и признак опасности для содержимого | `shared/ui` |

`confirm(...)` возвращает `Observable<boolean>`, который выдает ровно одно
значение и завершается. Отказ приходит и тогда, когда окно закрыто без выбора:
для вызывающего «закрыл» и «отменил» - одно и то же.

Альтернатива - отдать домену `ModalService.open(ConfirmationDialog, ...)`.
Отклонена: каждый вызывающий собирал бы окно сам, тексты кнопок и пресет
размера расползлись бы по доменам, а `presentation` домена получил бы знание о
`ModalService` без нужды.

### `ModalService.open()` возвращает `ModalRef`, `ModalRef` несет результат

`open()` возвращает `ModalRef` или `null`, если окно не открылось (уже открыто
другое). `ModalRef` получает `close(result?)` и поток закрытия с этим
результатом; источники закрытия, не принадлежащие содержимому (кнопка, `Escape`,
фон), закрывают без результата.

Тип результата - минимальный для текущей задачи: `boolean`, а не обобщенный
`ModalRef<R>`. Обобщение вводим, когда появится второй тип результата.

Существующие потребители (`create-chat`, `update-profile`, `change-password`,
`change-avatar`) возвращаемое значение не читают - их вызовы не меняются.

### Use case удаления повторяет форму соседних use case домена

`DeleteChatService` (слой `application`, `providedIn` не root - предоставляется
там же, где остальные use case домена) держит `isSubmitting`, шлет
`succeeded$` на успехе, вызывает `NOTIFIER` в обоих исходах и перезагружает
список через `ChatListService.loadChats()`.

Успех **Удаления чата** сопровождается **Уведомлением**, в отличие от создания
**Чата** и **Добавления участника**: там результат виден на экране сам, а
исчезновение **Чата** без подтверждения читается как сбой.

Локальное вычеркивание **Чата** из списка вместо `loadChats()` отклонено:
`ChatListService` остается единственным местом, где состав списка берется из
внешнего API.

### Уход с адреса удаленного чата делает presentation

После `succeeded$` шапка **Выбранного чата** уводит навигацию на `/`:
`application` про `Router` не знает. Порядок - сначала перезагрузка списка, потом
уход с адреса; порядок не наблюдаем в спеке, но так список не успевает мигнуть
удаленным **Чатом**.

### Уровни тестов

| Сценарий спеки                                                             | Уровень                                                       |
| -------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Удаление чата: подтверждение, исходы, **Уведомления**, перезагрузка списка | application (`DeleteChatService`)                             |
| `DELETE /chats` и чтение `created_by`                                      | infrastructure (`chat.api`, `chat.mapper`, `HttpChatGateway`) |
| Видимость действия, доступное имя, уход на `/`                             | component (`SelectedChatHeader`)                              |
| Ответы подтверждения, отказ при закрытии без выбора, опасное действие      | component (`ConfirmationService`, `ConfirmationDialog`)       |
| Результат закрытия и ссылка на окно                                        | component (`ModalService`, `ModalRef`)                        |
| Окно подтверждения целиком                                                 | e2e, скриншотный, тег `@visual`                               |

## Risks / Trade-offs

- `created_by` не объявлено в `properties` `ChatsResponse` → проверяется первым
  запросом к реальному API на первом же блоке; если поля нет, источником права
  становится `role` из `/chats/{id}/users`, а спека **Удаления чата** не
  меняется - меняется только `design.md`.
- `ModalService.open()` меняет сигнатуру → возвращаемое значение необязательно к
  использованию, существующие вызовы остаются как есть.
- Окно закрывается до ответа API, и **Чат** исчезает из списка позже ответа →
  между согласием и **Уведомлением** экран какое-то время показывает **Чат**,
  которого уже нет; это осознанный обмен на невозможность подвесить окно, у
  запросов таймаут не гарантирован.
- Макет приведен в соответствие с решением до реализации: артборд `DeleteChat`
  больше не показывает «запрос идет» и ошибку внутри окна, а показывает вопрос
  и два исхода с **Уведомлениями**; реализация сверяется с ним, а не наоборот.

## Migration Plan

Отдельной миграции нет: изменение аддитивное, обратной несовместимости для
существующих экранов не вносит.
