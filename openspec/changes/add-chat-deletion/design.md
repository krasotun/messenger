## Context

Мотивация - `proposal.md`, требования - дельты спеков в `specs/`.

Ограничения, которые формируют решение:

- `ModalService.open()` возвращает `void`, а `ModalRef.close()` не несет
  результата: узнать исход открытой модалки сегодня нечем.
- `shared/ui` не импортирует домены (ESLint `no-restricted-imports`), поэтому
  примитив подтверждения не может знать ни про **Чаты**, ни про **Шлюз**.
- `ChatDto` не объявляет `created_by`, хотя внешнее API его отдает:
  приложение сейчас **Создателя чата** отбрасывает на маппере. В
  `swagger.json` поле есть в примерах `ChatsResponse` и `ChatDeleteResponse`,
  но не в `properties`; наличие в живом ответе `GET /chats` проверено
  2026-09-05.
- Прецедент похода в соседний домен уже есть: `chats` берет
  `SearchUsersService` и `User` из публичного API `@domains/identity-access`.
  Тем же путем берется `CurrentSessionService`.
- Мок-бэкенд не отдает `created_by` и не реализует `DELETE /chats`. Без
  правки мока действие не появится ни в браузере, ни в e2e.

## Goals / Non-Goals

**Goals:**

- Примитив подтверждения в `shared/ui`, пригодный для любого необратимого
  действия, а не только для **Удаления чата**.
- Приложение читает **Создателя чата** и решает по нему, показывать ли
  действие.

**Non-Goals:**

- Общий механизм результата для всех модалок: `ModalService.open()` остается
  `void`, требование «Единое событие закрытия» не меняется. Исход различает
  только примитив подтверждения.
- Показ **Создателя чата** в интерфейсе и передача этой роли другому
  **Пользователю**.
- Чтение `role` из состава **Участников чата**: роль остается делом внешнего
  API, приложение ее не знает.
- Исключение **Участника чата** (`DELETE /chats/users`) - это issue #96.
- Архивация **Чата** (`/chats/archive`).

## Decisions

### Подтверждение - сервис поверх модалки, а не новый вид модалки

`ConfirmService.confirm(options): Observable<boolean>` открывает через
`ModalService` собственное содержимое и сам различает исход. Потребитель
подписывается на один поток и не видит ни `ModalRef`, ни портала.

Альтернативы:

- **`ModalService.open()` возвращает `ModalRef` с результатом.** Общее
  решение, но ломает требование «Единое событие закрытия» и задевает уже
  работающую модалку создания **Чата** ради единственного нового случая.
- **Колбэк `onConfirm` в `inputs`.** Дешевле всего, но передача функций через
  `setInput` в проекте не встречается - конструкция была бы чужой.

### Действие передается в примитив, а не выполняется после закрытия

`options.action?: () => Observable<unknown>`. Пока действие выполняется, окно
живет, кнопки недоступны, закрытие не срабатывает; при успехе окно
закрывается и поток отдает `true`, при ошибке окно остается и показывает
**Ошибку приложения**.

Иначе примитив пришлось бы либо оставить синхронным - и тогда ошибку удаления
показывать было бы негде, кроме шапки - либо отдать наружу ручку управления
окном (`setSubmitting`, `setError`, `close`), а с ней и возможность забыть его
закрыть.

Закрытие во время выполнения действия запрещено намеренно: закрытое окно
некуда вернуть ошибку, а отменять уже ушедший запрос приложение не умеет.

### Состояние отправки живет в примитиве, а не в сервисе домена

`DeleteChatService` отдает `Observable<void>` и не заводит ни статуса, ни
`errorMessage` - в отличие от `CreateChatService`, где форма живет в домене.
Здесь ход отправки и ошибку показывает окно подтверждения; вторая копия
состояния расходилась бы с первой.

Текст ошибки примитив берет из `ApplicationError` (`@shared/errors`) - общий
тип, а не доменный, границы слоев не нарушаются.

### Признак «я создал этот чат» - из списка чатов, а не из состава участников

`SelectedChatHeader` сравнивает `currentUser()?.id` из `CurrentSessionService`
с `createdBy` **Чата**, который уже лежит в `ChatListService`. Отдельного use
case не заводим: это одно сравнение над загруженными данными.

Альтернатива - брать `role: 'admin'` из `GET /chats/{id}/users`: это ровно то
условие, которое проверяет сам `DELETE /chats`. Отклонена, потому что роль
приезжает вторым запросом, и до его ответа действие пришлось бы прятать -
кнопка появлялась бы с задержкой. `created_by` приходит вместе со списком, и
**Выбранный чат** уже знает про него все.

Расхождение остается риском: API решает по роли, приложение показывает по
создателю. На учебном API создатель и есть единственный `admin`.

### Кнопка удаления - только значок

В шапке уже стоит «+ Member» с подписью; вторая подписанная кнопка рядом
утяжеляет строку, а корзина узнаваема без слов. Видимой подписи нет, поэтому
доступное имя обязательно - этого требует спека.

Значок кладется inline-`svg` в шаблон: примитива иконок в проекте нет, и
заводить его внутри этого change незачем. Помечается тем же `TODO(#49)`, что
уже стоит на глифе закрытия в `modal-shell.html`.

Доступное имя пишется по-английски, как видимые подписи в чатах. Прецедент в
`modal-shell.html` русский (`aria-label="Закрыть"`) - расхождение остается и
выравнивается отдельной правкой, не этим change.

### Уход с адреса удаленного чата

После успеха `SelectedChatHeader` перезапрашивает список через
`ChatListService.loadChats()` и уводит навигацию на `/`. Иначе адрес
`/:chatId` остался бы на удаленном **Чате**, и сработал бы сценарий
«Выбранного чата не существует» - **Ошибка приложения** как результат
собственного действия.

### ADR не пишется

Порог `docs/adr/README.md` не пройден по условию «тяжело откатить»: у
примитива подтверждения один потребитель, смена формы контракта - правка двух
файлов.

## Вводимые сущности

| Имя                   | Ответственность                                | Слой                |
| --------------------- | ---------------------------------------------- | ------------------- |
| `ConfirmService`      | Задать вопрос, провести действие, отдать исход | `shared/ui/confirm` |
| `ConfirmModalContent` | Разметка вопроса: тексты, кнопки, ошибка       | `shared/ui/confirm` |
| `ConfirmOptions`      | Тексты и необязательное действие               | `shared/ui/confirm` |
| `DeleteChatService`   | Вызов **Шлюза** для **Удаления чата**          | `chats/application` |
| `DeleteChatInput`     | `chatId`                                       | `chats/application` |
| `createdBy`           | **Создатель чата** в модели **Чата**           | `chats/application` |

Меняются: `ChatGateway` (метод `deleteChat`), `HttpChatGateway`, `ChatApi`
(`DELETE /chats`), `ChatDto` и маппер (`created_by`), `SelectedChatHeader`,
публичные `index.ts` домена и `shared/ui`, `mock-backend`, `docs/api/README.md`
(заметка о расхождении примеров и `properties`).

## Уровни тестов по сценариям

| Сценарий спеки                                                      | Уровень                                                                          |
| ------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| Действие подтверждено / Отказ кнопкой / Окно закрыто, а не отвечено | component                                                                        |
| Тексты задает вызывающий                                            | component                                                                        |
| Действие выполняется / успех / ошибка / повтор / отказ после ошибки | component                                                                        |
| Чат создан текущим пользователем / другим пользователем             | component (`SelectedChatHeader`)                                                 |
| Подтверждение отклонено                                             | component                                                                        |
| Чат удален                                                          | application (`DeleteChatService`) + component (перезапрос и уход с адреса) + e2e |
| Удаление отклонено                                                  | application + component                                                          |
| `DELETE /chats`, `created_by` в маппере                             | infrastructure                                                                   |
| Окно подтверждения на экране                                        | e2e `@visual`                                                                    |

## Risks / Trade-offs

- **Примитив с одним потребителем рискует быть спроектирован под него.** →
  Контракт держится на текстах и действии; ничего про **Чаты** в нем нет.
- **Окно нельзя закрыть, пока идет удаление.** → Запрос один и короткий;
  зависший запрос упрется в таймаут HTTP и вернет **Ошибку приложения**.
- **Приложение показывает действие по создателю, а API решает по роли.** →
  На учебном API `admin` - создатель **Чата**; если они разойдутся, API
  ответит ошибкой и сработает сценарий «Удаление отклонено».
- **`created_by` не объявлено в `properties` схемы `ChatsResponse`.** → Поле
  есть в примерах спеки и в живом ответе (проверено 2026-09-05); расхождение
  фиксируется заметкой в `docs/api/README.md`, чтобы следующая сверка контракта
  на нем не споткнулась.
