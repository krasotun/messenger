# Дизайн: чаты - список, создание и добавление участника

## Context

Мотивация - в `proposal.md`. Здесь важны три ограничения текущего кода.

Внешнее API не дает собрать **Чат** и его состав одним запросом: `POST /chats`
принимает только название и отвечает одним `id`, участники добавляются
отдельным `PUT /chats/users`. Поэтому «создать чат с участниками» как единое
действие невозможно в принципе, и это не выбор дизайна.

`resolveAvatarUrl` лежит в `identity-access/infrastructure` и берет базовый
адрес аргументом, а не инъекцией. Это делает переезд в `shared` безопасным:
запрет `shared` зависеть от `core` функцию не задевает.

Границы ESLint разрешают импорт домена из домена, но только через публичный
API (`@domains/<name>`), не глубже.

## Goals / Non-Goals

**Goals:**

- Домен `chats` не знает про HTTP и получает мир только через **Шлюз**.
- Все состояния экрана - загрузка, пусто, ошибка, «чат не выбран» - описаны
  поведением, а не оставлены верстке.
- Переезд `resolveAvatarUrl` не меняет поведения и проверяется существующими
  тестами.

**Non-Goals:**

- Кэширование и оптимистичные обновления списка **Чатов**.
- Пагинация: `GET /chats` принимает `offset` и `limit`, но список берется
  целиком; постраничность вводится, когда появится реальный объем.
- Обобщение popover **Поиска пользователя** в переиспользуемый примитив.

## Decisions

### Домен `chats` и его состав

| Имя                               | Ответственность                                                                    | Слой           |
| --------------------------------- | ---------------------------------------------------------------------------------- | -------------- |
| `Chat`                            | **Чат** в списке: id, название, аватар, счетчик непрочитанных, последнее сообщение | application    |
| `ChatUser`                        | **Участник чата**: id, имя, аватар                                                 | application    |
| `ChatGateway` + `CHAT_GATEWAY`    | контракт домена к API чатов                                                        | application    |
| `ChatListService`                 | список **Чатов** и его перезагрузка                                                | application    |
| `CreateChatService`               | use case создания **Чата**                                                         | application    |
| `ChatUsersService`                | состав **Выбранного чата**                                                         | application    |
| `AddChatUserService`              | use case **Добавления участника**                                                  | application    |
| `HttpChatGateway` + DTO и мапперы | реализация контракта поверх HTTP                                                   | infrastructure |
| `ChatList`, `ChatListItem`        | список и его строка                                                                | presentation   |
| `CreateChatForm`                  | форма создания в модалке                                                           | presentation   |
| `SelectedChatHeader`              | шапка **Выбранного чата**                                                          | presentation   |
| `ChatUserStack`                   | стек аватаров **Участников чата** и «+K»                                           | presentation   |
| `AddChatUserPanel`                | **Поиск пользователя** и **Добавление участника** в popover                        | presentation   |

### Поиск пользователя остается за `identity-access`

Искомая вещь - **Пользователь**, а не **Чат**, поэтому `searchUsers`
добавляется в существующий `UserGateway`. Наружу через `index.ts` уезжает use
case `SearchUsersService`, а не токен `USER_GATEWAY`: чатам нужен поиск, а не
смена пароля и аватара.

Альтернативы: отдельный `USER_SEARCH_GATEWAY` - обобщение раньше повторения;
собственный шлюз в `chats` - две точки знания об одном endpoint.

Порог `docs/adr/README.md` это решение не проходит: оно удивит без контекста и
имело настоящие альтернативы, но откатывается правкой нескольких файлов - не
выполнено условие «тяжело откатить».

В `identity-access` впервые появляется модель `User` рядом с `CurrentUser`:
чужой **Пользователь** доступен только на чтение.

### `resolveAvatarUrl` переезжает в `shared/resources`

Не в `shared/ui/avatar`: функция строит адрес ресурса внешнего API и к UI
отношения не имеет - примитив `Avatar` принимает уже готовый адрес.

### Выбранный чат живет в маршруте

`/:chatId` - дочерний маршрут списка. `/` это «чат не выбран», не отдельное
состояние сервиса. Перезагрузка страницы сохраняет выбор, адрес **Чата**
делится ссылкой.

### После создания - перезапрос списка

`POST /chats` отдает только `id`. Собирать строку списка локально значило бы
выдумывать аватар, счетчик и последнее сообщение, поэтому `ChatListService`
перезапрашивает `GET /chats`. То же после **Добавления участника** для состава
**Выбранного чата**.

### Поиск идет по вводу

`POST /user/search` ищет по началу **Логина** - подсказка по ходу ввода и есть
его назначение. В `src` еще нет `debounceTime` + `switchMap`; прецедент
создается здесь, отмена предыдущего запроса обязательна, иначе поздний ответ
перезапишет ранний.

Пустой ответ (`200` и `[]`) - не **Ошибка приложения**: показывается «Никого не
нашли», отдельно от состояния «еще не искали».

### Пять состояний панели добавления

`AddChatUserPanel` различает их явно, потому что три из пяти выглядят как
«пусто» и сливаются, если не разделить:

| Состояние           | Что показано                                                    |
| ------------------- | --------------------------------------------------------------- |
| поле пустое         | подсказка «Начните вводить логин»                               |
| запрос идет         | предыдущие результаты остаются, чтобы список не мигал           |
| нашли               | строки **Пользователей**, клик по строке добавляет              |
| ответ пуст          | «Никого не нашли» - нейтральный текст, не **Ошибка приложения** |
| `400` на добавлении | текст `reason` под списком, панель остается открытой            |

Успех отдельного сообщения не получает: панель закрывается, а добавленный
**Участник чата** появляется в стеке шапки - результат виден там, где он
живет. Поэтому стек в шапке обязателен, а не украшение: без него у
**Добавления участника** нет видимого результата.

### Где показывается каждая ошибка

Ошибка привязана к области, которая не сработала, а не к экрану целиком:

| Ошибка                                    | Место           | Что остается рабочим       |
| ----------------------------------------- | --------------- | -------------------------- |
| список **Чатов** не загрузился            | колонка списка  | создание **Чата**          |
| адрес указывает на несуществующий **Чат** | правая панель   | список **Чатов**           |
| создание **Чата** отклонено               | форма в модалке | введенное название         |
| **Добавление участника** отклонено        | панель поиска   | найденные **Пользователи** |

Состояние «не смогли загрузить» никогда не рисуется как «пусто»: у пустого
списка своя формулировка, и подмена скрыла бы сбой. Фон панели ошибки берет
неиспользованные токены `--color-surface-error-start` и
`--color-surface-error-end`.

Повтор есть только у списка **Чатов**: там ошибка перекрывает весь экран и
без повтора выход один - перезагрузка страницы. У несуществующего **Чата**
повторять нечего - адрес не станет валиднее от второй попытки; у форм повтор и
есть повторная отправка.

### Уровни тестов

| Поведение                                                    | Уровень                   |
| ------------------------------------------------------------ | ------------------------- |
| загрузка списка, пусто, ошибка                               | application               |
| создание **Чата** и перезапрос списка                        | application               |
| **Поиск пользователя**, debounce, отмена предыдущего запроса | application (fake timers) |
| **Добавление участника** и обновление состава                | application               |
| мапперы DTO, `resolveAvatarUrl`                              | infrastructure            |
| строка списка, шапка, стек с «+K», состояния popover         | component                 |
| `/:chatId`, «чат не выбран», несуществующий **Чат**          | routing                   |
| создание **Чата**; **Добавление участника**                  | e2e, два отдельных теста  |
| экран чатов по умолчанию                                     | e2e `@visual`             |

Второму e2e-тесту нужен готовый **Чат**. Он создается прямым HTTP-запросом к
`mock-auth-backend` из фикстуры Playwright до навигации, а не прокликиванием
UI: иначе тест повторяет первый и падает по чужой причине.

## Risks / Trade-offs

- Поздний ответ поиска перезапишет свежий → `switchMap` плюс
  `takeUntilDestroyed`; отмена проверяется отдельным application-тестом.
- «+K» выглядит кликабельным, но никуда не ведет → это текст, а не кнопка: без
  hover, фокуса и указателя. Проверяется component-тестом.
- Счетчик непрочитанных нечем обнулить без переписки и будет гореть всегда →
  принято сознательно; поведение описывается в спеке как отображение числа из
  ответа API, а не как «непрочитанные пользователя».
- `mock-auth-backend` вырастает вдвое одним файлом `server.ts` → разделение по
  ресурсам делается в отдельной секции tasks, до добавления чатов.
- `home-page` удаляется вместе со спекой → заглушка, поведения не несет;
  маршрут `/` перестает существовать без списка **Чатов**, что и проверяет
  routing-тест.
