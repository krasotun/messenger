## Context

Мотивация - в `proposal.md`, требования - в `specs/`. Здесь только то
состояние кода, которое определяет подход.

Шесть форм приложения устроены одинаково: `FormGroup` живет в компоненте,
кнопка получает `[disabled]="isSubmitting()"`, а `onSubmit` начинается с
`if (form.invalid) { form.markAllAsTouched(); return; }`. **Флоу отправки**
существует фабрикой `createAuthFlowState` в `identity-access/application`;
`CreateChatService`, `AddChatUserService` и `DeleteChatService` повторяют его
телом класса.

Две детали кода ограничивают решение:

- Отправка блокирует форму через `form.disable({ emitEvent: false })`. Поток
  состояния формы на это молчит, поэтому производное значение «можно
  отправлять» во время отправки не обновляется, и `isSubmitting` из выражения
  `[disabled]` убрать нельзя.
- Несовпадение повтора пароля - валидатор уровня группы, а не поля:
  `changePasswordForm.errors.repeatMismatch`. Правило «кнопка недоступна, пока
  форма невалидна» покрывает его автоматически, но сообщение под полем
  по-прежнему держится на `touched` этого поля.

Границы слоев закреплены в ESLint: `application` не импортирует
`@angular/forms` и `@shared/ui/*`.

## Goals / Non-Goals

**Goals:**

- Одно место, которое отвечает на «можно ли сейчас отправлять», и одна форма
  выражения `[disabled]` во всех шести формах.
- Одно определение **Флоу отправки** на приложение.
- **Флоу отправки** остается доступным из `application`, не протаскивая туда
  знание об Angular-формах.

**Non-Goals:**

- Signal Forms (`@angular/forms/signals`) в Angular 21 позволяют выразить
  валидность сигналом нативно, но переводить на них шесть форм - отдельная
  работа, несоизмеримая с этой.
- Показ ошибок полей не меняется: он уже работает по `touched`.
- Блокировка формы во время отправки остается такой, как есть.

## Decisions

### Две вещи, а не одна

**Флоу отправки** и доступность кнопки - отдельные сущности в отдельных местах
`shared`, хотя спека описывает их одной capability.

- `shared/submit-flow` - **Флоу отправки**. Не зависит от Angular-форм, его
  импортируют сервисы `application`.
- `shared/forms` - доступность кнопки. Зависит от `@angular/forms`, его
  импортирует только `presentation`.

Альтернатива - сложить обе в `shared/forms` - отклонена: `application`
импортировал бы модуль с именем `forms`, и граница, которую ESLint охраняет
запретом на `@angular/forms`, размылась бы по смыслу, оставшись формально
целой. Чтобы это не произошло позже, запрет на `@shared/forms/*` из
`application` добавляется в `eslint.config.js` рядом с существующим запретом на
`@shared/ui/*`.

### Доступность - фабрика сигнала, не директива

`createSubmitAvailability(form, { requireChanges })` возвращает
`Signal<boolean>`; шаблон получает `[disabled]="isSubmitting() || !canSubmit()"`.
Подписка на `form.events` (единый поток по значению, статусу, `pristine` и
`touched`) перечитывает `form.valid` и `form.dirty`.

Директива на кнопке рассматривалась и отклонена: `isSubmitting` живет в
компоненте, а не в форме, поэтому директива все равно не смогла бы владеть
выражением целиком - получился бы примитив, который решает половину задачи и
требует второго биндинга рядом. Фабрика же повторяет прием, который в проекте
уже есть: `createAuthFlowState` и `createUserSearchState` - ровно такие
фабрики сигналов.

`requireChanges` - необязательный флаг, его просит только форма
**Редактирования профиля**. Условием выбран `dirty`, а не `touched`: `touched`
становится истинным от фокуса без изменения значения, и защита от сохранения
неизмененного **Профиля** протекала бы.

### Имя **Флоу отправки** в коде

`createAuthFlowState` -> `createSubmitFlowState`, файл
`shared/submit-flow/create-submit-flow-state.ts`. Русский термин **Флоу
отправки** уже был верным - неверным было только английское имя, названное по
одному из случаев употребления. Это закрывает развилку `auth flow` в
`## Flagged ambiguities`; запись переносится в решенные.

### `markAllAsTouched` уходит, охранное условие остается

`markAllAsTouched()` вызывать неоткуда: кнопка недоступна, нажатия не будет.
Проверка `if (form.invalid) return` в `onSubmit` сохраняется как охранное
условие - она дешева и защищает от отправки в обход кнопки.

### Уровни тестов

| Сценарий спеки                                                                    | Уровень                                                    |
| --------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `shared-form-submission`: состояние одной попытки отправки (все сценарии)         | unit на фабрику **Флоу отправки**                          |
| `shared-form-submission`: доступность кнопки отправки (все сценарии)              | unit на фабрику доступности + component spec на host-форме |
| `shared-form-submission`: запрет отправки неизмененной формы (все сценарии)       | unit на фабрику доступности                                |
| `identity-access`: отправка невалидной формы во всех пяти формах                  | component spec формы                                       |
| `identity-access`: сохранение недоступно до изменений, становится доступным после | component spec `update-profile-form`                       |
| `identity-access`: повтор не совпадает с новым паролем                            | component spec `change-password-form`                      |
| `identity-access`: остальные сценарии измененных требований                       | уже покрыты, тесты не переписываются                       |
| `chats`: название не указано, название стерли после ввода                         | component spec `create-chat-form`                          |
| Кнопка недоступна на открытом экране                                              | существующие скриншотные e2e, снимки пересматриваются      |

Переход трех сервисов `chats` на общий **Флоу отправки** своих сценариев не
добавляет: их application specs уже описывают `isSubmitting` и `succeeded$` и
остаются критерием того, что поведение не поехало.

### Вводимые сущности

| Имя                        | Ответственность                                               | Слой                 |
| -------------------------- | ------------------------------------------------------------- | -------------------- |
| `createSubmitFlowState`    | состояние одной попытки отправки и однократное событие успеха | `shared/submit-flow` |
| `createSubmitAvailability` | производное «можно ли отправлять» из состояния формы          | `shared/forms`       |

## Risks / Trade-offs

- Пустая форма с недоступной кнопкой не объясняет, чего не хватает, пока
  человек не тронул поля → обратную связь дает показ ошибки поля после ухода с
  него; он уже работает и в этом change не меняется. Вариант с пояснением
  рядом с кнопкой рассматривался и отклонен как отдельная работа по макетам.
- `form.events` молчит при `disable({ emitEvent: false })` → `isSubmitting`
  остается в выражении `[disabled]`; убирать его как «теперь лишнее» нельзя.
- Переименование **Флоу отправки** трогает публичное API домена
  `identity-access` → правка механическая, ее держат существующие тесты пяти
  форм.
- Скриншотные e2e снимают экраны с пустыми полями, то есть ровно те состояния,
  где кнопка стала недоступной → снимки разойдутся и пересматриваются глазами,
  а не переснимаются вслепую.

## Migration Plan

Миграции нет: изменение целиком внутри клиента, внешнее API и формат запросов
не затронуты. Откат - возврат коммита.
