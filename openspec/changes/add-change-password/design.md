## Context

**Смена пароля** - часть capability `identity-access`. Мотивация - в
`proposal.md`, требования - в `specs/identity-access/spec.md`.

Готовая опора: `USER_GATEWAY` уже отделен от `AUTH_GATEWAY`, флоу отправки
формы переиспользуется через `createAuthFlowState`, модалка открывается
`ModalService`. Смена пароля повторяет схему **Редактирования профиля**, но
короче на один шаг: ответ бэкенда пустой, обновлять нечего.

Контракт endpoint'а сверен со Swagger учебного API и дописывается в
`infrastructure/user-api.contract.md`:

| Use case        | Method | Path             | Body                         | Success         |
| --------------- | ------ | ---------------- | ---------------------------- | --------------- |
| Change Password | PUT    | `/user/password` | `oldPassword`, `newPassword` | `200`, тела нет |

Ограничения, которые формируют решения ниже:

- Поля запроса в **camelCase**, в отличие от snake_case в `/user/profile`.
- Тела ответа нет; отдельного статуса для неверного старого пароля тоже нет -
  только `400` с `reason`.
- `ModalService.open` игнорирует вторую модалку, пока открыта первая.

## Goals / Non-Goals

**Goals:**

- Смена пароля как самостоятельный use case, не связанный с редактированием
  профиля.
- Presentation не знает о транспорте, application - о модалке и формах.
- Сценарий проверяется e2e на мок-бэкенде.

**Non-Goals:**

- Правила сложности пароля: их нет и на **Регистрации**, вводить их здесь
  значило бы получить пароли, которые нельзя сменить на равноценные.
- Показ и скрытие пароля глазом, индикатор надежности.
- Восстановление забытого пароля: другой сценарий и другого endpoint'а в API
  нет.
- Тост или баннер об успехе: успех выражается закрытием формы, как в
  редактировании профиля; примитива уведомлений в `shared/ui` нет.

## Decisions

### Отдельный пункт меню, а не секция в модалке профиля

Смена пароля открывается своей модалкой из меню текущего пользователя рядом с
«Edit profile».

Альтернативы: вкладка внутри модалки профиля - модалка начала бы обслуживать
два use case и два флоу отправки одновременно; переход по ссылке из профиля -
из-за запрета двух модалок это была бы замена одной другой с потерей
несохраненных правок профиля.

### Метод в существующем `USER_GATEWAY`

`changePassword` добавляется в `UserGateway`, новый токен не вводится: это тот
же ресурс `user` того же бэкенда.

### Ввод без результата

Use case принимает модель входа с `oldPassword` и `newPassword` и возвращает
`Observable<void>`: возвращать нечего, модели результата не заводим. Текущая
сессия не трогается - это ключевое отличие от редактирования профиля, где
`CurrentSessionService` обновлялся из ответа.

### Повтор пароля не покидает presentation

Повтор нового пароля - поле формы и кросс-валидатор на уровне `FormGroup`. В
модель входа use case оно не входит: бэкенд о нем не знает, и его проверка -
правило ввода, а не правило домена.

### Ответ читается как текст

Запрос выполняется с `responseType: 'text'`, как в sign-in: успех - это статус
`200`, а не тело. С дефолтным json-разбором пустой ответ или `OK` привел бы к
ошибке парсинга на успешном сценарии.

### Ошибка - через существующий маппер

`mapAuthError` с generic-сообщением-запасом, как в остальных методах шлюза.
Отдельного сценария для неверного старого пароля нет: бэкенд не дает отличить
его от прочих `400`, а `reason` показывается как есть.

### Форма сбрасывается при каждом открытии

Экземпляры формы и модалки создаются заново на каждое открытие, а use case
сбрасывает флоу отправки после успеха и при закрытии формы. Так повторное
открытие не показывает старую ошибку.

### Мок-бэкенд получает тот же endpoint

`PUT /user/password` в `mock-auth-backend`: `401` без сессии, `400` с `reason`
на неверный старый пароль, иначе `200` и обновленный пароль в хранилище. Без
этого e2e не может проверить ни успех, ни ошибку.

## Уровни тестов по сценариям

| Сценарий из спеки                      | Уровень                       |
| -------------------------------------- | ----------------------------- |
| Открытие формы смены пароля            | component (меню)              |
| Успешная смена пароля                  | application + component + e2e |
| После успешной смены нет навигации     | application                   |
| Бэкенд отклоняет смену пароля          | application + component + e2e |
| Повтор не совпадает с новым паролем    | component                     |
| Отправка формы с незаполненными полями | component                     |
| Форма заблокирована во время отправки  | component                     |
| Отмена смены пароля                    | component                     |
| Повторное открытие формы после ошибки  | component                     |
| Адрес, метод, camelCase тела запроса   | infrastructure                |

## Вводимые сущности

| Имя                           | Ответственность                                 | Слой           |
| ----------------------------- | ----------------------------------------------- | -------------- |
| `ChangePasswordInput`         | Входная модель use case: старый и новый пароль  | application    |
| `ChangePasswordService`       | Use case смены пароля и его флоу отправки       | application    |
| `UserGateway.changePassword`  | Расширение контракта шлюза                      | application    |
| `ChangePasswordRequestDto`    | Тело запроса в camelCase                        | infrastructure |
| `changePasswordRequestMapper` | Отображение входной модели в DTO                | infrastructure |
| `UserApi.changePassword`      | Вызов `PUT /user/password`                      | infrastructure |
| `ChangePasswordForm`          | Форма с тремя полями и кросс-валидацией повтора | presentation   |
| `ChangePasswordModalContent`  | Обертка формы для модалки, закрытие по успеху   | presentation   |

## Risks / Trade-offs

- camelCase тела запроса против snake_case соседнего `/user/profile` → маппер
  пишется по Swagger, а не по аналогии, аномалия фиксируется в
  `user-api.contract.md`, формат проверяется infrastructure-тестом.
- Пустое тело успешного ответа при дефолтном json-разборе выглядит как ошибка
  → `responseType: 'text'` и тест, который это закрепляет.
- Мок-бэкенд становится вторым источником правды о поведении endpoint'а и
  может разойтись с реальным API → в моке воспроизводятся только статусы и
  `reason` из Swagger, без собственных правил валидации.
- Отсутствие правил на пароль означает, что пользователь может задать пустую
  по смыслу, но непустую строку → сознательный компромисс ради согласованности
  с **Регистрацией**; ужесточение правил - отдельный change сразу для обоих
  экранов.
