## Context

Мотивация - в `proposal.md`, раздел Why.

Текущее состояние, которое определяет подход:

- Шлюзы вызывают `mapHttpError(error, fallback)` внутри
  `catchError` -> `throwError`. У `currentSession` перед этим стоит своя ветка:
  ответ `401` - это не ошибка, а `CurrentSessionStatus.Anonymous`.
- `createAuthFlowState` в `identity-access/application` уже реализует нужную
  фабрику отправки; ей пользуются пять сервисов домена. Два сервиса чатов
  (`create-chat`, `add-chat-user`) повторяют ее руками, два других
  (`chat-list`, `chat-users`) повторяют руками ее загрузочный вариант.
- Границы импортов в ESLint: `application` не импортирует `@shared/ui/*`, но
  остальной `@shared` ему доступен; сам `@shared` не знает про `@core` и
  `@domains`. Фабрика состояния в `@shared/flow` этих границ не нарушает.
- Термины **Флоу отправки** (`submit flow`) и **Флоу загрузки** (`load flow`)
  уже записаны в `CONTEXT.md`.

## Goals / Non-Goals

**Goals:**

- Одно место, где ошибка внешнего API превращается в **Ошибку приложения** для
  вызывающей стороны шлюза.
- Одно место, где живет переход состояний use case и сообщение об ошибке.
- Внешне наблюдаемое поведение не меняется: те же состояния, те же тексты, тот
  же порядок переходов.

**Non-Goals:**

- Показ ошибки в `presentation` не трогаем: каждый экран продолжает читать
  `errorMessage` и рисовать его как рисует. Тосты - #112.
- `CurrentSessionService` остается на своем `CurrentSessionStatus`: `Unknown`
  против `Anonymous` - доменное различие, а не состояние флоу.
- Обобщения «на будущее» в фабриках нет: только то, что уже повторяется в
  девяти сервисах.

## Decisions

### Ошибка мапится RxJS-оператором в конце pipe шлюза

Вводится `toApplicationError(fallbackMessage)` - оператор в `@shared/errors`,
слой `shared`. Ответственность: перехватить ошибку потока и пробросить дальше
**Ошибку приложения**, собранную существующим `mapHttpError`. Сам `mapHttpError`
не меняется.

Альтернатива - HTTP-интерцептор, превращающий любой `HttpErrorResponse` в
**Ошибку приложения** централизованно. Отклонена: запасное сообщение у каждого
вызова свое, и его пришлось бы возить через `HttpContext` от шлюза к
интерцептору - то есть то же дублирование, только длиннее. Плюс ветка `401` в
`currentSession` превратилась бы в исключение из общего правила.

Альтернатива - базовый класс шлюза с защищенным `request(obs, fallback)`.
Отклонена: наследования в `src` сейчас нет, а по конвенции проекта отсутствие
прецедента - сигнал, что конструкция проекту чужая.

Порог ADR это решение не проходит: не выполнено условие «тяжело откатить» -
переход на интерцептор позже затрагивает три файла шлюзов.

### Флоу отправки и Флоу загрузки - две фабрики, а не одна

Решение и причины - в
[ADR 2026-09-05](../../../docs/adr/2026-09-05-two-flows-for-use-case-state.md).

Состав вводимых сущностей, слой `shared` (каталог `@shared/flow`):

| Имя                      | Ответственность                                                                                                    |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| `SubmitFlowStatus`       | Состояния попытки отправки: `Idle`, `Submitting`, `Success`, `Error`                                               |
| `createSubmitFlowState`  | Сигналы `status`, `errorMessage`, `isSubmitting` и переходы `startSubmitting`, `markSuccess`, `markError`, `reset` |
| `LoadFlowStatus`         | Состояния попытки загрузки: `Idle`, `Loading`, `Loaded`, `Error`                                                   |
| `createLoadFlowState<T>` | То же плюс сигнал `data` и переходы `startLoading`, `markLoaded(data)`, `markError`                                |

`createSubmitFlowState` - это переехавший `createAuthFlowState` без изменений в
поведении; переименование и переезд идут одним шагом, чтобы не править одни и
те же файлы дважды.

### Флоу загрузки держит данные

`createLoadFlowState<T>(initialData)` владеет сигналом `data`, а `markLoaded`
одним вызовом кладет данные и переводит статус в `Loaded`. Иначе связка
«данные приехали - статус `Loaded`» осталась бы копией в каждом сервисе, а
рассинхрон между ними - ровно то, что change убирает.

Производные вычисления остаются в сервисе: `isEmpty` у `ChatListService`
осмысленно только для списка и в фабрику не поднимается.

### Данные при ошибке не очищаются

`markError` меняет статус и сообщение, но не трогает `data`. Это сохраняет
сегодняшнее поведение `chat-list` и `chat-users`: при неудачной перезагрузке
список остается на экране, а не пропадает.

## Уровни тестов

| Что проверяется                                                                      | Уровень        |
| ------------------------------------------------------------------------------------ | -------------- |
| `toApplicationError`: причина из ответа, запасное сообщение, истекший предел времени | infrastructure |
| Шлюзы отдают **Ошибку приложения**, `currentSession` на `401` отдает `Anonymous`     | infrastructure |
| Переходы `createSubmitFlowState` и `createLoadFlowState`, данные при ошибке          | application    |
| Девять use-case-сервисов: те же состояния и сообщения, что и до change               | application    |
| Экраны показывают ошибку и состояние загрузки как раньше                             | component      |

Новых сценариев тесты не заводят: change ничего не добавляет к поведению.
Существующие спеки сервисов и компонентов - это и есть сеть безопасности, и
править их по ходу переезда можно только в части имен статусов.

## Risks / Trade-offs

- Переезд девяти сервисов правит и их спеки: подгонка теста под сломавшуюся
  реализацию здесь неотличима от честной правки имени статуса. → Ветки блоков
  ревьюятся отдельно; в диффе спеки допустима замена имени перечисления и
  ничего больше. Утверждения о состояниях и сообщениях остаются дословно теми
  же.
- `@shared/flow` может со временем стать свалкой любого состояния. → Каталог
  назван по термину: внутри только **Флоу отправки** и **Флоу загрузки**,
  все прочее туда не кладется.
- `createLoadFlowState<T>` - первый generic в `@shared` вне типов. → Параметр
  ровно один и выводится из `initialData`, вызывающей стороне ничего указывать
  руками не нужно.
- Change идет тремя блоками, между которыми `main` живет обычной жизнью. →
  Каждый блок самодостаточен: после любого из них проект собирается и тесты
  зеленые.

## Migration Plan

Флаги и обратная совместимость не нужны: все вызывающие стороны внутри
репозитория и переезжают вместе с change. Порядок блоков - в `tasks.md`.
Откат - обычный revert PR блока: блоки независимы друг от друга.
