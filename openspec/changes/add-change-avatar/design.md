## Context

**Смена аватара** - часть capability `identity-access`. Мотивация - в
`proposal.md`, требования - в `specs/identity-access/spec.md`.

Готовая опора та же, что у **Смены пароля**: `USER_GATEWAY` отделен от
`AUTH_GATEWAY`, флоу отправки формы - `createAuthFlowState`, модалка -
`ModalService`, базовый URL и `withCredentials` для API-запросов подставляет
`apiRequestInterceptor` по токену `API_BASE_URL`.

Контракт endpoint'а сверен со Swagger учебного API:

| Use case      | Method | Path                   | Body                                        | Success                 |
| ------------- | ------ | ---------------------- | ------------------------------------------- | ----------------------- |
| Change Avatar | PUT    | `/user/profile/avatar` | `multipart/form-data`, поле `avatar` (file) | `200`, `CurrentUserDTO` |

Отличия от соседних endpoint'ов `/user/*`:

- Тело запроса - не JSON, а `multipart/form-data`. `HttpClient.put` с телом
  `FormData` сам не проставляет `Content-Type` - браузер выставляет его с
  правильным `boundary`; вручную заголовок не задаем.
- Допустимые форматы перечислены в Swagger буквально: JPEG, JPG, PNG, GIF,
  WebP. Лимит размера не документирован - полагаемся на `400 { reason }`.
- Ответ - полноценный `CurrentUserDTO`, как у **Редактирования профиля**, а не
  пустой текст, как у **Смены пароля**.

Отдельная, не связанная с этим use case напрямую проблема: `avatar` в
`CurrentUserDTO` - относительный путь (`/path/to/avatar.jpg`), а не URL.
Ресурсы этого API отдаются с отдельного префикса под тем же базовым URL:
`https://ya-praktikum.tech/api/v2/resources<path>`. Префикс проверен запросом:
`/resources<path>` отвечает `404`, `/api/v2/resources<path>` - `401` без
сессии, то есть путь существует и требует той же сессии, что и API. Без резолва
в абсолютный URL `<img>` не покажет ни новый, ни любой другой аватар. Так как
`identity-access` - единственный сегодняшний потребитель аватаров, резолв
делается здесь; `shared/ui/avatar` остается доменно-нейтральным и просто
рисует переданный `imageUrl` как есть.

## Goals / Non-Goals

**Goals:**

- Смена аватара как самостоятельный use case, независимый от редактирования
  профиля - как задано в `CONTEXT.md`.
- Presentation не знает о транспорте и о формате `multipart/form-data`,
  application не знает о `File`/`FormData` напрямую за пределами входной
  модели.
- Аватар (свежесмененный и любой пришедший с бэкенда) корректно отображается
  как `<img src>`.

**Non-Goals:**

- Обрезка, поворот, ресайз изображения на клиенте - Swagger не требует
  конкретных размеров, бэкенд принимает файл как есть.
- Клиентский лимит размера файла - формат не документирует лимит; вводить
  свой означало бы гадать без источника правды.
- Удаление аватара (сброс в `null`) - у API нет отдельного метода на это,
  только на замену.
- Резолв URL для аватаров других пользователей (в чатах) - `identity-access`
  знает только о текущем пользователе; когда появится показ чужих аватаров,
  функция резолва станет общей, но это отдельный change.

## Decisions

### Блок в модалке редактирования профиля, а не отдельная модалка

В отличие от **Смены пароля**, у смены аватара нет своего пункта меню и своей
модалки: `ChangeAvatarForm` встраивается в `UpdateProfileModalContent` над
`UpdateProfileForm` и открывается тем же «Edit profile». Две формы в одной
модалке остаются независимыми use case: у каждой свой сервис
(`ChangeAvatarService`, `UpdateProfileService`) и свой флоу отправки,
отправка одной не трогает другую - именно это, а не отдельная модалка,
обеспечивает независимость действия, зафиксированную в `CONTEXT.md` («у нее
свой endpoint и своя форма»).

Причина отклонить отдельную модалку - не техническая (`ModalService.open`
действительно не поддерживает две модалки разом, как и у смены пароля), а
UX: аватар - это часть того же экрана «отредактировать себя», и заставлять
пользователя открывать второй диалог ради одного поля - лишний шаг.

Альтернатива - слить в один use case с одним submit (аватар сохраняется
вместе с полями профиля): отклонена, она меняет зафиксированный в
`CONTEXT.md` термин («смена аватара - отдельное действие») и потребовала бы
правки словаря и спеки **Редактирования профиля**, а не только этой спеки.

### Метод в существующем `USER_GATEWAY`

`changeAvatar` добавляется в `UserGateway`: тот же ресурс `user` того же
бэкенда, отдельный токен не нужен.

### Резолв URL - в мапперe DTO, а не в компоненте

`currentUserMapper` (infrastructure) при мапинге `CurrentUserDTO -> CurrentUser`
превращает относительный `avatar` в абсолютный URL. Domain-модель `CurrentUser`
после мапинга содержит готовый к показу URL - presentation (`Avatar`,
`current-user-avatar-menu`) не меняется в этой части и не знает о хосте
ресурсов.

Альтернатива - резолвить в `Avatar` (shared/ui) или в
`current-user-avatar-menu`: отклонена, `shared/ui` не должен знать о доменах и
хостах API, а resolve в presentation домена дублировался бы всюду, где
`CurrentUser.avatar` читается впредь.

### Базовый URL ресурсов - новый токен, по аналогии с `API_BASE_URL`

Вводится `RESOURCES_BASE_URL` (значение
`https://ya-praktikum.tech/api/v2/resources`
для обеих сред - реальный бэкенд один и тот же и для `npm start`, и для
превью) и чистая функция `resolveAvatarUrl(path, baseUrl)`. Инъекция базового
URL в маппер происходит через параметр функции, а не через DI: мапперы в
проекте (`currentUserMapper`, `updateProfileRequestMapper`) сегодня везде
чистые функции без инъекций; вызывающая сторона (`HttpUserGateway`,
`HttpAuthGateway`) уже внутри DI-контекста и передает значение из
инжектированного токена.

### Input use case - `File`, а не `FormData`

`ChangeAvatarInput` - `{ file: File }`. Сборка `FormData` (`append('avatar',
file)`) - ответственность мапперa в infrastructure, как
`updateProfileRequestMapper` собирает DTO: application не знает о
транспортном формате тела запроса.

### Превью через `URL.createObjectURL`

Форма показывает превью выбранного файла до отправки через
`URL.createObjectURL(file)`, отзывая предыдущий URL при выборе нового файла
или уничтожении компонента (`URL.revokeObjectURL`) - иначе объектные URL
текут до конца сессии вкладки.

### Мок-бэкенд получает тот же endpoint

`PUT /user/profile/avatar` в `mock-auth-backend`: `401` без сессии, `400` с
`reason` на неподдерживаемый формат (миметип запроса), иначе `200` с
обновленным `avatar` (путь к сохраненному файлу) в ответе. Без этого e2e не
может проверить ни успех, ни ошибку.

## Уровни тестов по сценариям

| Сценарий из спеки                            | Уровень                       |
| -------------------------------------------- | ----------------------------- |
| У пользователя есть аватар (резолв URL)      | infrastructure + component    |
| Открытие формы смены аватара                 | component (модалка профиля)   |
| Выбор файла показывает превью                | component                     |
| Выбор файла неподдерживаемого формата        | component                     |
| Успешная смена аватара                       | application + component + e2e |
| После успешной смены нет навигации           | application                   |
| Бэкенд отклоняет смену аватара               | application + component + e2e |
| Отправка формы без выбранного файла          | component                     |
| Форма заблокирована во время отправки        | component                     |
| Отмена смены аватара                         | component                     |
| Повторное открытие формы после ошибки        | component                     |
| Адрес, метод, состав `FormData` тела запроса | infrastructure                |

## Вводимые сущности

| Имя                         | Ответственность                                             | Слой           |
| --------------------------- | ----------------------------------------------------------- | -------------- |
| `ChangeAvatarInput`         | Входная модель use case: `{ file: File }`                   | application    |
| `ChangeAvatarResult`        | Результат use case: обновленный `CurrentUser`               | application    |
| `ChangeAvatarService`       | Use case смены аватара и его флоу отправки                  | application    |
| `UserGateway.changeAvatar`  | Расширение контракта шлюза                                  | application    |
| `RESOURCES_BASE_URL`        | Токен базового URL ресурсов бэкенда                         | core           |
| `resolveAvatarUrl`          | Чистая функция: относительный путь -> абсолютный URL        | infrastructure |
| `changeAvatarRequestMapper` | Сборка `FormData` из `ChangeAvatarInput`                    | infrastructure |
| `UserApi.changeAvatar`      | Вызов `PUT /user/profile/avatar`                            | infrastructure |
| `ChangeAvatarForm`          | Форма выбора файла с превью, встраивается в модалку профиля | presentation   |

## Risks / Trade-offs

- `RESOURCES_BASE_URL` жестко закодирован на реальный хост API для обеих сред
  → мок-бэкенд не отдает файлы по `/resources`, значит e2e на аватар с превью
  реального изображения не проверяют путь через реальный хост; сценарий
  "аватар показывается после смены" на e2e проверяется по факту вызова API и
  обновления состояния, а не по загрузке байтов картинки.
- Префикс ресурсов в Swagger не описан и проверен только запросами по коду
  ответа (`404` против `401`), а не загруженной картинкой: под сессией
  проверить его в этом окружении нечем → если окажется неверным, миграция -
  точечная правка одной константы.
- Ресурсы требуют сессии, а `<img>` шлет куку сама только при
  `SameSite=None`: локальная разработка и превью ходят на бэкенд кросс-сайтом
  → если кука окажется `Lax`, аватар не загрузится ни у кого, и понадобится
  проксирование или отдельный публичный префикс.
- `multipart/form-data` - первый нестандартный формат тела в
  `identity-access` → маппер и infrastructure-тест фиксируют состав `FormData`
  явно, чтобы регрессия была видна.
- Утечка `Object URL` превью при неаккуратном жизненном цикле формы →
  `revokeObjectURL` при смене файла и в `ngOnDestroy`/`DestroyRef`, закрыто
  component-тестом.
- Мок-бэкенд становится вторым источником правды о поведении endpoint'а и
  может разойтись с реальным API → в моке воспроизводятся только статусы,
  без собственных правил валидации сверх обязательности файла.
