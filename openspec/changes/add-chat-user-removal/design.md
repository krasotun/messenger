## Context

Мотивация - в `proposal.md`, требования - в дельтах спек этого change.

Что ограничивает подход:

- Маршрут `:chatId` сейчас рендерит только `SelectedChatHeader`: места под
  переписку и под что-либо рядом с ней нет. Роутер переиспользует этот
  компонент при переходе между **Чатами**, поэтому состав грузится `effect` по
  `chatId`.
- Шапка **Выбранного чата** уже решает, кто **Создатель чата**: `created_by`
  **Чата** из `GET /chats` сравнивается с `id` **Текущего пользователя**
  (`canDeleteChat` в `SelectedChatHeader`). Там же спрашивается подтверждение
  **Удаления чата** через `ConfirmationService`, и там же предоставлен
  `DeleteChatService`.
- Состав **Чата** держит `ChatUsersService` (`providedIn: 'root'`) в сигнале
  `chatUsers`; перезагружает его `loadChatUsers(chatId)`. Так уже делает
  `AddChatUserService` после успеха.
- `ChatUserStack` - картинка без взаимодействия: четыре **Аватара** и `+K`.
- `Popover` закрывается по щелчку снаружи, в том числе внутри модалки поверх
  него: это норма CDK, #219 закрыт как not planned. Поэтому состав в popover
  не пережил бы окно подтверждения.
- `ModalShell` ставит `cdkTrapFocusAutoCapture`: закрывшись, модалка
  возвращает фокус на элемент, который был в фокусе до нее, если он еще в DOM.
- `ConfirmationDialog` собирает вопрос как
  `{confirmLabel} <b>{subject}</b>? {message}`: предмет всегда стоит перед
  вопросительным знаком.
- Внешнее API: `DELETE /chats/users` с телом `{ users: number[], chatId }`, как
  у `PUT /chats/users`; ответ `200` без JSON-тела.
- Прототип трех вариантов - ветка `96-prototype-remove-member`, вердикт в #96.
- Макет: канвас экрана чатов,
  https://claude.ai/artifact/YDqakVRTWPoZB7pTATbETE.

## Goals / Non-Goals

**Goals:**

- Состав **Чата** стоит рядом с перепиской, а не поверх нее, и не зависит от
  того, какие оверлеи открываются над экраном.
- Исход **Исключения участника** переживает закрытие состава **Чата**.
- Право на исключение берется из того же места, что право на **Удаление
  чата**, без второго источника.

**Non-Goals:**

- Полная выгрузка состава постранично - #213. Число в заголовке состава и `+K`
  считаются по тому, что вернул один запрос без `offset`/`limit`.
- Раскладка на узких экранах: панель сужает место под переписку, адаптив - не
  в этом change.
- Перевод `+ Add member` из popover в ту же панель.
- Выход **Текущего пользователя** из **Чата** (исключение самого себя).
- Исключение нескольких **Участников чата** одним запросом, хотя тело
  `DELETE /chats/users` принимает массив.
- `aria-expanded` у `Popover`: примитив ее не ставит, это правка всех его
  потребителей. У кнопки стека признак ставится, потому что это не `Popover`.
- Пометка **Создателя чата** в списке состава.

## Decisions

### Состав - боковая панель, а не оверлей

Состав открывается панелью справа под шапкой, в одной строке с местом под
переписку; переписка сужается, а не перекрывается. Панель - обычный элемент
раскладки, поэтому щелчок снаружи и `Escape` ее не касаются, а окно
подтверждения открывается поверх без правок `ModalService`. Закрывают панель
повторное нажатие на стек и кнопка `✕` в ее заголовке.

Альтернативы сравнивались прототипом:

- popover состава - закрывается под окном подтверждения, а держать его
  открытым значило учить `ModalService` перехватывать щелчки для чужих
  оверлеев. Отклонен вместе с этой правкой;
- модалка состава с подтверждением вторым шагом - обходится без второго окна,
  но не использует `ConfirmationDialog` и не меняет заголовок на шаге
  подтверждения без правки `ModalShell`. Отклонена;
- экран состава на месте переписки с подтверждением в строке - закрыл бы
  переписку, когда она появится, и расходится с **Удалением чата** по форме
  подтверждения. Отклонен.

### Маршрутный компонент выбранного чата

Вводится:

| Имя                     | Ответственность                                                                                                                           | Слой           |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | -------------- |
| `SelectedChat`          | маршрут `:chatId`: грузит состав, решает, кто **Создатель чата**, держит признак открытого состава, раскладывает шапку, переписку, панель | `presentation` |
| `ChatUsersPanel`        | содержимое панели: заголовок с числом, строки, пометка своей строки, кнопки исключения и закрытия, события о намерениях                   | `presentation` |
| `RemoveChatUserService` | исключить **Участника чата**, перезагрузить состав, сообщить исход **Уведомлением**                                                       | `application`  |
| `RemoveChatUserInput`   | `chatId` и `userId` исключаемого                                                                                                          | `application`  |

`SelectedChat` забирает у шапки то, что нужно обоим соседям: `effect` загрузки
состава по `chatId`, поиск **Чата** в списке и признак права, который
переименовывается из `canDeleteChat` в `isChatCreator` - теперь он решает два
действия. Шапка получает **Чат**, `isChatCreator` и признак открытого состава
входами и отдает `membersToggled`; **Удаление чата** остается в шапке вместе с
`DeleteChatService`.

`RemoveChatUserService` предоставлен в `providers` `SelectedChat`, и
подтверждение спрашивает он же по `removeRequested` панели. Так use case
живет дольше панели, и исход виден после ее закрытия.

Альтернатива - шапка рисует панель сама, абсолютно спозиционированной под
собой, как в прототипе. Отклонена: панель легла бы поверх переписки, а не
рядом, - ровно то, от чего уходим.

Альтернатива - use case в `providers` панели, как у `AddChatUserPanel`.
Отклонена: панель уничтожается при закрытии, а сценарий «Исход виден после
закрытия состава» требует, чтобы use case ее пережил.

### Признак открытого состава - сигнал, а не адрес

`membersOpen` - сигнал `SelectedChat`. Роутер переиспользует компонент при
смене `chatId`, поэтому панель остается открытой при переходе к другому
**Чату** без отдельного кода. Перезагрузка страницы закрывает панель.

Альтернатива - дочерний маршрут `:chatId/members`. Отклонена: ссылка на
открытый состав не нужна, а маршрут потянул бы guard'ы и тесты роутинга.

Пока `ChatUsersService` отдает ошибку, панель не рендерится, хотя
`membersOpen` сохраняется: ошибку показывает шапка, и дублировать ее в панели
незачем.

### Стек аватаров становится кнопкой в шапке, а не внутри себя

Шапка оборачивает `<app-chat-user-stack>` в `<button>` с доступным именем
`Members: N`, `aria-expanded` по признаку открытого состава и `aria-controls`
на панель. `ChatUserStack` остается картинкой без событий: что открывается по
нажатию, решает тот, кто держит кнопку.

Альтернатива - кнопка внутри `ChatUserStack`. Отклонена: стек пришлось бы учить
про состав, а его единственная работа - показать **Аватары**.

### Фокус

- Открытие стеком переводит фокус на заголовок панели `Members · N`
  (`tabindex="-1"`): скринридер сразу читает число.
- После успешного **Исключения участника** фокус тоже уходит на заголовок:
  кнопка исключенного исчезла вместе со строкой, и без этого фокус упал бы на
  `body`. `SelectedChat` делает это по `succeeded$`, если панель еще открыта.
- После отказа фокус возвращает `cdkTrapFocusAutoCapture` - на кнопку
  исключения, строка еще на месте.
- `✕` панели возвращает фокус на кнопку стека в шапке.

### Длинный состав прокручивается внутри списка

Панель занимает всю высоту под шапкой; прокручивается только список строк,
заголовок `Members · N` с кнопкой закрытия в прокрутку не входит.

### Кнопка исключения видна всегда

`✕` стоит в каждой строке, кроме своей, без наведения; при наведении и фокусе
становится цветом опасного действия. Скрытая до наведения кнопка не находится
на тач-экранах, а e2e и скриншоту пришлось бы сначала наводить указатель.

### Исключение и удаление чата - на хелпере действия без формы

`RemoveChatUserService` и `DeleteChatService` строятся на новом
`createActionFlowState()` из `@shared/submit-flow` - паре к
`createFormSubmitFlowState()` для действий без формы. Он отдает `succeeded$` и
`markSuccess`, без `isSubmitting`: у обоих сервисов его никто не читает -
кнопки на время запроса не блокируются, а повторное действие до ответа API
перекрывает подтверждение. Имя «Form» у прежнего хелпера на них не ложилось, и
`DeleteChatService` переводится на новый хелпер в этом же change, а его
`isSubmitting` уходит. `createFormSubmitFlowState()` строится на
`createActionFlowState()` и добавляет `isSubmitting`; его API не меняется.
Наследование базового класса отвергнуто: в проекте состояние отправки
везде держится полем-хелпером, и класс не смог бы взять и действие, и форму.

`RemoveChatUserService` на успехе перезагружает состав и шлет
`notifier.success('Remove member', 'Member removed')`, на отказе -
`notifier.error('Failed to remove member', message)`.

Успех сопровождается **Уведомлением**, как у **Удаления чата**, хотя строка
исчезает на глазах: панель могли закрыть до ответа API, и тогда
**Уведомление** - единственный след исхода.

Шлюз получает `removeChatUser(input): Observable<void>`, `ChatApi` -
`DELETE /chats/users` с телом `{ users: [userId], chatId }` и
`responseType: 'text'`, как у `addChatUser`: ответ `200` без JSON, и разбор
пустого тела как JSON упал бы. Тело у `DELETE` передается опцией `body`, как
уже сделано в `deleteChat`.

Локальное вычеркивание строки до ответа отклонено по той же причине, что у
**Удаления чата**: единственный источник состава - внешнее API через
`ChatUsersService`.

### Тексты окна подтверждения

`ConfirmationDialog` ставит предмет перед вопросительным знаком, поэтому
вопрос «Remove Ivan Ivanov from Analytics Q3?» им не собрать. Тексты:
заголовок `Remove member`, предмет - имя **Участника чата**, `message` -
`They leave "<title>" and can be added back later.`, кнопка - `Remove`,
`isDangerous` не задан. Название **Чата** в `message` выполняет сценарий
«Подтверждение запрошено».

### ADR

Порог `docs/adr/README.md` не проходит ни одно решение по условию «тяжело
откатить»: `SelectedChat` - обертка вокруг существующей шапки, панель -
компонент домена `chats`. ADR не заводим.

| Открытие и закрытие состава, щелчок мимо и `Escape`, переход к другому чату, состав не загрузился, фокус | component (`SelectedChat`)                        |
| Видимость действия создателю, автор неизвестен                                                           | component (`SelectedChat`)                        |

| Панель состава у **Создателя чата**, Состав не помещается (прокрутка)                                    | e2e, скриншотный, тег `@visual`                   |

## Risks / Trade-offs

- Внешнее API может запрещать исключение не-админу или отказывать иначе, чем
  ожидаем → отказ в любом виде уходит **Уведомлением** с текстом `reason`, а
  действие и так показано только **Создателю чата**. Живой запрос к API
  проверяется на блоке use case.
- Перенос загрузки состава и права из шапки в `SelectedChat` задевает спеки
  шапки и роутинга `chats-page` → переезд делается отдельным блоком без
  нового поведения, прежние сценарии **Удаления чата** и **Выбранного чата**
  должны остаться зелеными.
- Панель сужает место под переписку → на узких экранах переписке может не
  хватить ширины; адаптив вне скоупа.
- Фокус на кнопку стека после `✕` требует от `SelectedChat` дотянуться до
  элемента шапки → шапка отдает метод фокуса, `SelectedChat` берет ее через
  `viewChild`.
- Состав без `offset`/`limit` может быть неполным, если лимит API по умолчанию
  меньше состава → число в заголовке и `+K` занижены так же, как сейчас;
  решается в #213.
- После согласия строка остается в списке до ответа API → обмен на единственный
  источник состава; между согласием и **Уведомлением** проходит один запрос.
