## Context

Мотивация - в `proposal.md`, требования - в дельтах спек этого change.

Что ограничивает подход:

- Шапка **Выбранного чата** уже решает, кто **Создатель чата**: `created_by`
  **Чата** из `GET /chats` сравнивается с `id` **Текущего пользователя**
  (`canDeleteChat` в `SelectedChatHeader`). Там же спрашивается подтверждение
  через `ConfirmationService`, и там же предоставлен `DeleteChatService`.
- Состав **Чата** держит `ChatUsersService` (`providedIn: 'root'`) в сигнале
  `chatUsers`; перезагружает его `loadChatUsers(chatId)`. Так уже делает
  `AddChatUserService` после успеха.
- `ChatUserStack` - картинка без взаимодействия: четыре **Аватара** и `+K`.
- `Popover` закрывается по `outsidePointerEvents()` оверлея CDK. Диспетчер CDK
  (`OverlayOutsideClickDispatcher`, CDK 21.2) обходит оверлеи сверху вниз,
  пропускает те, у кого нет подписчиков `outsidePointerEvents`, и
  останавливается на первом, внутри которого был щелчок. `ModalService`
  слушает только `backdropClick()` и `Escape`, поэтому щелчок по кнопке в
  окне подтверждения сейчас доходит до popover под ним как щелчок «снаружи».
- `ConfirmationDialog` собирает вопрос как
  `{confirmLabel} <b>{subject}</b>? {message}`: предмет всегда стоит перед
  вопросительным знаком.
- Внешнее API: `DELETE /chats/users` с телом `{ users: number[], chatId }`, как
  у `PUT /chats/users`; ответ `200` без JSON-тела.
- Макет: артборды `ChatMembers` и `RemoveMember` канваса экрана чатов,
  https://claude.ai/artifact/YDqakVRTWPoZB7pTATbETE (версия 17).

## Goals / Non-Goals

**Goals:**

- Исход **Исключения участника** переживает закрытие состава **Чата**.
- Любая модалка поверх любого popover перестает его закрывать - без знания
  `Popover` о модалках.
- Право на исключение берется из того же места, что право на **Удаление
  чата**, без второго источника.

**Non-Goals:**

- Полная выгрузка состава постранично - #213. Число в заголовке состава и `+K`
  считаются по тому, что вернул один запрос без `offset`/`limit`.
- Выход **Текущего пользователя** из **Чата** (исключение самого себя).
- Исключение нескольких **Участников чата** одним запросом, хотя тело
  `DELETE /chats/users` принимает массив.
- `aria-expanded` и прочая ARIA-разметка у `Popover`: примитив ее не ставит и
  сейчас, это правка всех его потребителей.
- Пометка **Создателя чата** в списке состава.

## Decisions

### Состав - отдельный компонент, решения принимает шапка

Вводится:

| Имя                     | Ответственность                                                                                  | Слой           |
| ----------------------- | ------------------------------------------------------------------------------------------------ | -------------- |
| `ChatUsersPanel`        | содержимое popover состава: строки, пометка своей строки, кнопки исключения, событие о намерении | `presentation` |
| `RemoveChatUserService` | исключить **Участника чата**, перезагрузить состав, сообщить исход **Уведомлением**              | `application`  |
| `RemoveChatUserInput`   | `chatId` и `userId` исключаемого                                                                 | `application`  |

`ChatUsersPanel` получает состав, `id` **Текущего пользователя** и признак
«можно исключать» входами и отдает наружу `removeRequested` с исключаемым
**Участником чата**. Подтверждение спрашивает и use case вызывает
`SelectedChatHeader`, а `RemoveChatUserService` предоставлен в его
`providers` рядом с `DeleteChatService`.

Альтернатива - как у `AddChatUserPanel`: use case в `providers` самой панели,
подтверждение из панели. Отклонена: панель живет ровно столько, сколько открыт
popover, а подтверждение и право на действие уже живут в шапке. Два места,
спрашивающих подтверждение у одного экрана, и дублированный расчет права хуже,
чем одно событие наружу.

Признак права в шапке переименовывается из `canDeleteChat` в
`isChatCreator`: теперь он решает два действия, и имя по одному из них
вводило бы в заблуждение.

### Стек аватаров становится кнопкой в шапке, а не внутри себя

Шапка оборачивает `<app-chat-user-stack>` в `<button appPopover>` с доступным
именем `Members: N`. `ChatUserStack` остается картинкой без событий: кнопка и
popover - забота того, кто решает, что по нажатию открывается.

У шапки появляется второй `Popover`, поэтому `viewChild(Popover)` перестает
быть однозначным: оба триггера получают ссылки в шаблоне, и
`closeAddUserPopover()` берет свой по имени.

Альтернатива - кнопка внутри `ChatUserStack`. Отклонена: стек пришлось бы учить
про `Popover` и про содержимое состава, а его единственная работа - показать
**Аватары**.

### Popover остается открытым, потому что читает сигнал состава

Шаблон popover рендерится из шаблона шапки, и `ChatUsersPanel` получает
`chatUsers()` из `ChatUsersService`. После успеха `RemoveChatUserService`
вызывает `loadChatUsers(chatId)`, сигнал обновляется, и открытый список
перерисовывается сам. Отдельного «закрыть по успеху» нет, в отличие от
`AddChatUserPanel`.

Локальное вычеркивание строки до ответа отклонено по той же причине, что у
**Удаления чата**: единственный источник состава - внешнее API через
`ChatUsersService`.

### Use case повторяет форму `DeleteChatService`

`RemoveChatUserService` держит `isSubmitting` и `succeeded$` через
`createFormSubmitFlowState()`, на успехе перезагружает состав и шлет
`notifier.success('Remove member', 'Member removed')`, на отказе -
`notifier.error('Failed to remove member', message)`.

Успех сопровождается **Уведомлением**, как у **Удаления чата**, а не молчит,
как **Добавление участника**: строка исчезает из списка под окном
подтверждения, и без **Уведомления** это читается как сбой.

Шлюз получает `removeChatUser(input): Observable<void>`, `ChatApi` -
`DELETE /chats/users` с телом `{ users: [userId], chatId }` и
`responseType: 'text'`, как у `addChatUser`: ответ `200` без JSON, и разбор
пустого тела как JSON упал бы. Тело у `DELETE` передается опцией `body`, как
уже сделано в `deleteChat`.

### Модалка сама перехватывает щелчки внутри себя

`ModalService` подписывается на `overlayRef.outsidePointerEvents()` и ничего
по ним не делает. Подписчик заставляет диспетчер CDK считать модалку
получателем, и на щелчке внутри нее обход останавливается: popover под ней
этого щелчка не видит. Щелчок по фону по-прежнему «снаружи» для всех: фон не
входит в элемент окна, модалка закрывается по `backdropClick()`, а popover -
по своему `outsidePointerEvents`.

Альтернатива - `Popover` игнорирует щелчки, пока над ним есть другой оверлей.
Отклонена на разборе: `Popover` начал бы знать о чужих оверлеях, а правило
«модальное окно не закрывает то, что под ним» - свойство модалки.

Альтернатива - `eventPredicate` на оверлее popover. Отклонена: предикат видит
только событие, а не то, над каким оверлеем оно случилось, и повторял бы
проверку диспетчера руками.

Порог `docs/adr/README.md` решение не проходит по условию «тяжело откатить»:
это одна подписка в `ModalService`, и правило закреплено требованием спеки
`shared-ui-modal`. ADR не заводим.

### Тексты окна подтверждения

`ConfirmationDialog` ставит предмет перед вопросительным знаком, поэтому
вопрос из макета «Remove Ivan Ivanov from Analytics Q3?» им не собрать.
Тексты: заголовок `Remove member`, предмет - имя **Участника чата**,
`message` - `They leave "<title>" and can be added back later.`, кнопка -
`Remove`, `isDangerous` не задан. Название **Чата** в `message` выполняет
сценарий «Подтверждение запрошено». Артборд `RemoveMember` уже показывает этот
текст.

### Уровни тестов

| Сценарий спеки                                                                                   | Уровень                                           |
| ------------------------------------------------------------------------------------------------ | ------------------------------------------------- |
| Участник исключен, Исключение отклонено: перезагрузка состава, **Уведомления**, `succeeded$`     | application (`RemoveChatUserService`)             |
| `DELETE /chats/users` с телом, отказ как **Ошибка приложения**                                   | infrastructure (`ChatApi`, `HttpChatGateway`)     |
| Состав открыт, пометка своей строки, число, кнопки исключения и их доступные имена               | component (`ChatUsersPanel`)                      |
| Открытие и закрытие состава, доступное имя стека, видимость действия создателю, автор неизвестен | component (`SelectedChatHeader`)                  |
| Подтверждение запрошено и отклонено, согласие вызывает use case, состав остается открытым        | component (`SelectedChatHeader`)                  |
| Исход виден после закрытия состава                                                               | application (`RemoveChatUserService`) + component |
| Щелчок внутри модалки, `Escape`, щелчок по фону над popover                                      | component (`ModalService` вместе с `Popover`)     |
| Сквозное исключение с **Уведомлением**                                                           | e2e                                               |
| Popover состава у **Создателя чата**                                                             | e2e, скриншотный, тег `@visual`                   |

## Risks / Trade-offs

- Внешнее API может запрещать исключение не-админу или отказывать иначе, чем
  ожидаем → отказ в любом виде уходит **Уведомлением** с текстом `reason`, а
  действие и так показано только **Создателю чата**. Живой запрос к API
  проверяется на блоке use case.
- Подписка-заглушка на `outsidePointerEvents` в `ModalService` выглядит
  бессмысленной без контекста → рядом комментарий о диспетчере CDK, а
  поведение закреплено спекой `ModalService` вместе с `Popover`.
- Щелчок по фону окна подтверждения закрывает и popover состава → принято на
  разборе: щелчок мимо всего закрывает все. Отказ при этом остается отказом.
- Состав без `offset`/`limit` может быть неполным, если лимит API по умолчанию
  меньше состава → число в заголовке и `+K` занижены так же, как сейчас;
  решается в #213.
- После согласия строка остается в списке до ответа API → обмен на единственный
  источник состава; между согласием и **Уведомлением** проходит один запрос.
