## Context

Мотивация - в `proposal.md`, требования - в дельте `specs/chats/spec.md`.

Что ограничивает подход:

- Состав **Чата** держит `ChatUsersService` (`providedIn: 'root'`): сигналы
  `status`, `chatUsers`, `errorMessage`. Метод `loadChatUsers(chatId)` на
  каждый вызов делает отдельный `subscribe` на `CHAT_GATEWAY.chatUsers` и
  прежнюю подписку не трогает.
- Вызывающих два: `effect` в `SelectedChatHeader` на смену `chatId` и
  `AddChatUserService` после успеха. Третьим станет `RemoveChatUserService` из
  #96. Все зовут один и тот же метод, поэтому гонка лечится внутри сервиса.
- Повторы при смене **Чата** до сервиса не доходят: input `chatId` с
  `numberAttribute` сравнивает значение после преобразования, и `effect` не
  перезапускается на тот же **Чат**. Повторный вызов по тому же **Чату** -
  всегда намеренная перезагрузка.
- В проекте уже есть прецедент отмены устаревшего запроса:
  `createUserSearchState` в `user-search.state.ts` - поток ввода,
  `switchMap` на запрос, `catchError` внутри, `takeUntilDestroyed()`.
- Шапка читает только `chatUsers` и `errorMessage`; `status` и `isLoading` в
  интерфейсе не используются.

## Goals / Non-Goals

**Goals:**

- Применяется ответ или ошибка только последнего запроса состава.
- Прежний запрос отменяется по-настоящему (отписка от HTTP), а не
  доезжает до конца, чтобы его результат потом отбросили.
- Публичный API `ChatUsersService` не меняется, существующие ожидания его
  spec остаются зелеными.

**Non-Goals:**

- Очистка состава при смене **Чата** и индикатор загрузки - см. proposal.md.
- Перевод сервиса на SignalStore - это #159; там отмена переедет в
  `rxMethod` со `switchMap`.

## Decisions

### Состав вводимых сущностей

Новых сущностей нет. `ChatUsersService` (слой `application`) получает
приватный поток запрошенных `chatId` и одну подписку на него на все время
жизни сервиса.

### Отмена через `Subject` + `switchMap`

`loadChatUsers(chatId)` синхронно выставляет `Loading` и сбрасывает
`errorMessage`, затем кладет `chatId` в приватный `Subject`. В конструкторе
сервиса поток идет через `switchMap` в `gateway.chatUsers(chatId)`, результат
пишется в сигналы в `subscribe`.

- Почему синхронная часть остается в `loadChatUsers`: состояние
  «загружается» появляется в момент вызова, как сейчас, и текущие тесты на
  `Loading` не меняются.
- Альтернатива - хранить `Subscription` и делать `unsubscribe()` перед новым
  запросом. Работает так же, но в проекте уже есть прецедент со `switchMap`
  (`createUserSearchState`); два способа решать одну задачу в одном домене
  хуже одного.
- Альтернатива - `rxResource`. Отмена бесплатная, но это переделка
  состояния сервиса целиком - по сути #159 внутри багфикса.
- Альтернатива - отсев ответов по выбранному **Чату** без отмены: сервису
  пришлось бы знать, какой **Чат** выбран, а HTTP-запрос продолжал бы
  лететь.

### `catchError` внутри `switchMap`

Ошибка шлюза перехватывается во внутреннем потоке и превращается в
состояние `Error` с сообщением **Ошибки приложения**. Без этого первая же
ошибка завершила бы внешний поток, и следующие `loadChatUsers` молча ничего
бы не делали. Этот случай закрывает сценарий «Состав загружается после
ошибки».

### Без `distinctUntilChanged`

Повтор по тому же `chatId` не отбрасывается. Перезагрузка после
**Добавления участника** (и после исключения из #96) идет по тому же **Чату**;
отсев повторов проглотил бы ее, и новый **Участник чата** не появился бы в
шапке. Дублей при смене **Чата** нет и так - их отсекает сравнение input
`chatId` (см. Context).

### Время жизни подписки

`takeUntilDestroyed()` в конструкторе сервиса. Для `root` это время жизни
приложения, но `TestBed` пересоздает инжектор на каждый тест, и без
отписки подписки копились бы между тестами.

### ADR

Не пишем: не выполнено условие «тяжело откатить». Решение - несколько строк
внутри одного сервиса, и #159 все равно перепишет его на SignalStore.

### Уровни тестов

| Сценарий                                | Уровень                                    |
| --------------------------------------- | ------------------------------------------ |
| Участники помещаются                    | component (`ChatUserStack`), без изменений |
| Участников больше, чем помещается       | component (`ChatUserStack`), без изменений |
| Чат сменили до ответа                   | application (`ChatUsersService`)           |
| Прежний чат ответил ошибкой после смены | application (`ChatUsersService`)           |
| Состав загружается после ошибки         | application (`ChatUsersService`)           |

Порядок ответов в application spec задается управляемыми `Subject` вместо
ответов шлюза, без таймеров. e2e не добавляем: сценарий завязан на порядок
ответов, и тест на задержки сети был бы нестабильным. То, что шапка зовет
`loadChatUsers` на смену `chatId`, уже проверяет component spec
`SelectedChatHeader`.

## Risks / Trade-offs

- [Отмена срабатывает и для перезагрузки после **Добавления участника**, если
  следом пришла смена **Чата**] → Так и задумано: состав прежнего **Чата**
  больше не показывается, а при возврате загрузится заново.
- [Запрос, начатый до ухода со страницы **Чата**, доезжает в `root`-сервис]
  → Результат не виден; следующее открытие **Чата** загружает состав заново
  и отменяет его, если он еще в пути.
- [Ветка #96 правит соседние файлы домена] → Публичный API сервиса не
  меняется; кто смержится вторым, получит конфликт только при правке тех же
  строк `chat-users.service.ts`, а #96 их не трогает.
