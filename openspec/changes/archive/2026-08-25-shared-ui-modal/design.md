## Context

`shared/ui` - слой переиспользуемых примитивов без знания о доменах. Модалка
нужна ближайшему потребителю (редактирование профиля), но не должна ничего знать
про профиль. В проекте уже есть Angular CDK и похожий по механике примитив
`shared/ui/popover` с координатором единственности - решения стоит держать
согласованными.

Сейчас существует только заглушка `ModalService.open()`, бросающая
`Not implemented`.

## Goals / Non-Goals

Goals:

- Открыть произвольный компонент поверх приложения и закрыть его.
- Единое событие закрытия независимо от источника.
- Клавиатурный фокус не покидает открытую модалку и возвращается при закрытии.

Non-Goals:

- Конкретное содержимое модалки: в рамках change используется заглушка.
- Переключение содержимого внутри открытой модалки (например, подтверждение).
- Layout `header` / `main` / `footer` для содержимого - добавим, если появится
  необходимость.
- Стек из нескольких модалок.
- Передача результата наружу: модалка ничего не возвращает тому, кто ее открыл.

## Decisions

### Состав примитива

| Сущность       | Ответственность                                                                      | Слой              |
| -------------- | ------------------------------------------------------------------------------------ | ----------------- |
| `ModalService` | Открывает и закрывает модалку, хранит состояние единственности, владеет `OverlayRef` | `shared/ui/modal` |
| `ModalShell`   | Рамка, центрирование, затенение, кнопка закрытия, focus trap, хост для содержимого   | `shared/ui/modal` |
| `ModalRef`     | То, что содержимое получает через DI; единственный метод `close()`                   | `shared/ui/modal` |
| `ModalSize`    | Тип пресета ширины: `small` / `medium` / `large`                                     | `shared/ui/modal` |

Конкретные файлы под эти сущности перечислены в `tasks.md`.

### Данные в содержимое - через inputs

`open()` принимает компонент и значения его inputs; shell создает компонент
через `ComponentPortal` и проставляет значения `ComponentRef.setInput`.

Токен вида `MODAL_DATA` не вводим: содержимое остается обычным компонентом,
который можно отрендерить и протестировать вне модалки. Цена решения - имена
inputs становятся частью вызова `open()` и не проверяются типом так же строго,
как поля токена.

### Singleton-сервис поверх CDK Overlay

`ModalService` предоставляется в корне и хранит состояние текущей модалки. Он
открывает overlay через CDK и подписывается на события backdrop и `Escape`,
которые CDK дает из коробки. Кнопка закрытия - собственный элемент shell'а,
вызывающий закрытие явно.

Причина выбора сервиса, а не декларативного компонента в шаблоне: модалка
открывается из кода use case-экрана, а не из разметки, и должна быть доступна
из любого места без прокидывания через дерево компонентов.

### Shell-компонент

Содержимое рендерится внутри shell-компонента, который отвечает за рамку,
центрирование, размеры и кнопку закрытия. Само содержимое приходит как компонент
и получает свои входные данные; о существовании shell'а оно не знает.

Причина: разделение по причинам изменения. Оформление модалки меняется из-за
UI-инфраструктуры, содержимое - из-за требований своего экрана.

### ModalRef только для закрытия

Содержимое получает `ModalRef` через DI и вызывает `close()`. Прямых ссылок на
overlay, сервис или DOM у содержимого нет. Данные наружу не идут: содержимое
само отправляет их в свой use case, а состоянием владеет домен, а не тот, кто
открыл окно.

Отдельное событие `save(data)` рассмотрено и отклонено: у него не нашлось
подписчика. В ближайшем потребителе (`update-profile`) форма вызывает use case,
тот обновляет сессию, и после успеха форма закрывает себя сама - опенеру данные
не нужны. При этом отдельное событие порождало вопрос, закрывает ли `save`
окно, и давало два события на одно действие пользователя.

Если появится потребитель, которому нужен результат (например, confirm-диалог),
расширяем закрытие необязательным результатом - `close(result?)`, как в CDK
Dialog, - а не заводим второй канал.

Следствие для границ слоев: application-слой домена не должен зависеть от
`ModalRef`, `Overlay` и DOM. Связку «модалка - use case» держит presentation.

### Фокус - штатным focus trap из CDK

Shell оборачивает содержимое в `cdkTrapFocus` с включенным
`cdkTrapFocusAutoCapture`. Эта директива делает обе половины требования сразу:
переводит фокус внутрь области при инициализации и возвращает его на прежний
`activeElement` при уничтожении. Свой обход табуляции не пишем.

Начальный элемент фокуса не назначаем - по умолчанию это первый доступный
элемент модалки, а кнопка закрытия есть в shell'е всегда, так что фокусировать
заведомо есть что. Если конкретному содержимому понадобится другой стартовый
элемент, оно пометит его `cdkFocusInitial`: это работает как раз при включенном
autoCapture.

### Единственность через состояние сервиса

Повторный `open()` при активной модалке - defensive no-op: вторая модалка не
создается, первая не трогается. Это не пользовательский сценарий, а защита от
ошибки вызова.

Альтернатива - выбрасывать исключение - отклонена: падение приложения из-за
двойного клика хуже, чем игнорирование.

### Уровень теста по сценариям

Сквозного пользовательского сценария поверх примитива нет, поэтому e2e не
пишем - все требования закрываются component specs. Проверяем наблюдаемый факт,
а не внутренности CDK:

| Требование                               | Уровень   | Что утверждает тест                                                                             |
| ---------------------------------------- | --------- | ----------------------------------------------------------------------------------------------- |
| Открытие с произвольным содержимым       | component | Содержимое отрисовано, затенение присутствует                                                   |
| Блокировка и восстановление прокрутки    | component | Признак блокировки на `body` появился при открытии и снят при закрытии                          |
| Центрирование при изменении размера окна | component | Применена стратегия центрирования, а не конкретные пиксели                                      |
| Единое событие закрытия                  | component | Каждый источник дает одно событие закрытия, overlay уничтожен                                   |
| Управление фокусом                       | component | `document.activeElement` внутри модалки после открытия и на элементе-открывателе после закрытия |
| Размеры                                  | component | Класс пресета на элементе, фиксированной высоты нет                                             |
| Единственность                           | component | Повторный `open()` не создает второй overlay                                                    |

### Как проверяется этот change

У примитива нет потребителя внутри change - содержимым служит заглушка. Проверка
разложена так:

| Что проверяем                                                     | Чем                                                | Когда                    |
| ----------------------------------------------------------------- | -------------------------------------------------- | ------------------------ |
| Поведение (открытие, закрытие, фокус, размеры, единственность)    | Component specs с тестовой заглушкой в spec-файлах | В рамках этого change    |
| Внешний вид: центрирование, затенение, рамка, различие трех ширин | Разовая ручная проверка на локальном dev-сервере   | Перед завершением change |
| Работа в реальном сценарии                                        | Форма профиля и точка входа                        | Change `update-profile`  |

Ручная проверка делается временным кодом, который не коммитится: `open()` с
заглушкой вешается на любую доступную кнопку, `npm start`, смотрим три ширины,
длинное содержимое со скроллом, `Escape`, клик по фону, возврат фокуса - и
откатываем файл.

Постоянную демо-страницу или точку входа ради проверки не заводим. Скриншотный
`@visual` тест отклонен по той же причине: ему нужен маршрут или кнопка в
приложении, то есть тот же временный код, только оставленный навсегда. Так же
устроен уже существующий `shared/ui/popover`: component specs плюс проверка
глазами на первом настоящем потребителе.

## Risks / Trade-offs

- Тесты на центрирование и высоту по содержимому - это проверка вычисленных
  стилей; они хрупкие. Проверять наблюдаемый факт (класс пресета, отсутствие
  фиксированной высоты), а не пиксели.
- Блокировка скролла через CDK `BlockScrollStrategy` может конфликтовать с
  собственными стилями `body` - проверить восстановление прокрутки тестом.
- Внешний вид примитива не покрыт автотестами: component specs намеренно не
  проверяют пиксели, а e2e для него нет. Регрессия в оформлении обнаружится
  только глазами - на `update-profile` или позже. Осознанная цена того, что
  примитив пока никем не используется.
- Тесты на фокус проверяют наблюдаемый факт: `document.activeElement` внутри
  модалки после открытия и на элементе-открывателе после закрытия. Проверять
  внутренности focus trap не нужно - это чужая реализация.
