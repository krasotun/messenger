## Context

Профиль - часть capability `identity-access`. Текущий пользователь хранится в
`CurrentSessionService` и наполняется только из `GET /auth/user`. Обновление
профиля идет в отдельный endpoint `PUT /user/profile`, который возвращает
`CurrentUserDTO`.

Контракт endpoint'а описан в `infrastructure/user-api.contract.md`.

## Goals / Non-Goals

Goals:

- Обновить данные пользователя и синхронизировать состояние сессии.
- Держать application-слой свободным от деталей модалки и форм.

Non-Goals:

- Смена аватара: отдельный endpoint и отдельный сценарий.
- Смена пароля: отдельный endpoint и отдельные правила.
- Отдельная страница профиля: редактирование открывается в модалке.

## Decisions

### Источник обновленного состояния - ответ бэкенда

После успешного сохранения текущая сессия обновляется из `CurrentUserDTO` в
ответе, а не из того, что пользователь ввел в форму. Причина: бэкенд может
нормализовать значения, а `avatar` и `id` в запросе не участвуют вовсе.

### Отдельный gateway для user API

Auth и user - разные ресурсы бэкенда, поэтому вводится отдельный контракт
(`USER_GATEWAY` или аналогичный токен) рядом с `AUTH_GATEWAY`, а не расширяется
существующий. Причина: разные причины изменения и разные наборы операций.

### Обновление сессии внутри use case

Синхронизацию `CurrentSessionService` выполняет application-слой обновления
профиля, а не UI. Причина: это часть бизнес-правила «после успешного сохранения
состояние сессии актуально», а не деталь экрана.

### Навигации нет

Успешное сохранение не меняет маршрут. Решение о закрытии модалки принимает
presentation, получив успешный результат.

### Состояние flow

Переиспользуется `createAuthFlowState` (`Idle` / `Submitting` / `Success` /
`Error`), как в sign-in и sign-up: то же поведение блокировки формы и показа
ошибки.

## Risks / Trade-offs

- `login` уникален, но Swagger не документирует отдельный статус для конфликта.
  Полагаемся на `reason` из тела `400`; отдельного сценария для конфликта нет.
- Валидация полей должна совпадать с правилами регистрации (email, phone) -
  иначе одни и те же данные будут приниматься на одном экране и отклоняться на
  другом. Правила стоит переиспользовать, а не дублировать.
