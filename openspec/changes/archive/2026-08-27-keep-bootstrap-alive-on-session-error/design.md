## Context

См. `proposal.md` - Why. Существенно то, что `restoreCurrentSession()` вызывают
две стороны с несовместимыми ожиданиями:

- app initializer при старте - ему ошибка фатальна, потому что падающий поток
  из `provideAppInitializer` отменяет бутстрап;
- `SignInService` после успешного входа - ему ошибка нужна, чтобы перевести
  флоу отправки в `Error` и показать причину.

Шлюз уже различает `401` (штатный `Anonymous`) и техническую ошибку, а
`CurrentSessionService` уже выставляет `Anonymous` перед пробросом. Не хватает
только того, чтобы одна из двух вызывающих сторон ошибку поглощала.

## Goals / Non-Goals

Goals:

- старт приложения переживает любой отказ бэкенда при восстановлении сессии;
- поведение входа не меняется ни на шаг.

Non-Goals:

- отличать «сессии нет» от «спросить не удалось» в статусе сессии;
- показывать причину недоступности до попытки входа;
- повторять запрос восстановления сессии автоматически.

## Decisions

**Ошибку поглощает app initializer, а не сервис и не шлюз.**

Единственная вызывающая сторона, для которой ошибка фатальна, - старт
приложения, и только там она гасится. Состояние к моменту гашения уже
корректное: `CurrentSessionService` выставляет `Anonymous` до проброса.

Альтернативы:

- _Гасить в `CurrentSessionService`_ - отклонено: сервис обслуживает обе
  вызывающие стороны, и вход перестал бы видеть причину отказа, то есть
  человек получал бы форму, которая молча не срабатывает.
- _Гасить в шлюзе, приравняв любую ошибку к `Anonymous`_ - отклонено по той же
  причине, плюс шлюз потерял бы разницу между «сессии нет» и «бэкенд лежит»,
  которая понадобится, если позже захотим экран недоступности.

**ADR не заводится.** Порог `docs/adr/README.md` не проходит по первому
условию: решение откатывается снятием одной операции в инициализаторе.

## Risks / Trade-offs

- При лежащем бэкенде посетитель видит обычную форму входа и узнает о проблеме
  только после отправки → сообщение об ошибке входа уже показывается
  существующим флоу отправки; отдельный экран недоступности сознательно
  оставлен за границами change.
- Ошибка старта нигде не фиксируется, диагностировать «почему меня выкинуло на
  вход» по интерфейсу нельзя → браузерная консоль сохраняет сетевую ошибку
  запроса; отдельное логирование в проекте пока не заведено.

## Migration Plan

Миграции нет: поведение меняется только в отказном сценарии, состояние на
диске и на бэкенде не затрагивается. Откат - возврат одного коммита.

## Уровни тестов по сценариям

| Сценарий из дельты                          | Уровень                       |
| ------------------------------------------- | ----------------------------- |
| Активная сессия существует                  | application (без изменений)   |
| Активной сессии нет                         | application (без изменений)   |
| Ошибка при восстановлении сессии            | application (без изменений)   |
| Бэкенд недоступен при старте приложения     | core (спека app initializer)  |
| Вход после неудачного восстановления сессии | application (`SignInService`) |

E2E на этот сценарий не заводится: мок-бэкенд пришлось бы учить отвечать `500`
на `GET /auth/user` и держать этот режим на время загрузки страницы, что дороже
и хрупче, чем проверка инициализатора на уровне core.
